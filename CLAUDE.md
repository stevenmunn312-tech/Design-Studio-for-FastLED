# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

**Design Studio for FastLED** is a browser-based node-graph editor for designing LED lighting effects. Users wire together nodes on a canvas, see a real-time LED matrix preview, then generate FastLED/Arduino C++ firmware for upload to microcontrollers like the ESP32-S3.

Core user flow: drag nodes from sidebar → wire ports together → preview updates live → generate C++ → upload via the local build helper (`arduino-cli`/`fbuild`).

## Public beta — protect saved projects

The project is public and beta users may have saved projects, shared graphs, and
pattern libraries. Changes that rename, remove, or reshape node types,
properties, port ids, or persisted workspace data must either preserve existing
saves or include a deliberate migration and release note. Do not add speculative
migration layers, but do not assume external data can be discarded. Update tests
for both the new schema and any supported compatibility path.

**`main` is locked as of 2026-08-17** at the current public beta. Do not commit
to it — not features, not bug fixes, not documentation — unless the user
explicitly asks for a beta hotfix and says so in those terms.

**`Hardware` is the only active line.** It carries the roadmap work (the Board

compatibility: node types, properties, port ids, and persisted workspace data

The two branches are **deliberately isolated**. Do not merge between them in
either direction. `main` is a frozen record of what the beta testers are
running, and its value is that it stays exactly that; `Hardware` is free to
diverge as far as the roadmap needs. If something genuinely must reach beta
users, that is a decision for the user to make, not a routine merge.

Note that `main`'s own copy of this file still describes the earlier
merge-both-ways policy, because it was frozen before this correction landed.
`Hardware` is authoritative.

- **Use plain `git`** (`git add`, `git commit`, `git push`, `git pull`). Do **not**
  use `cortex git` here.

## Architecture

### Viewport contract

The supported desktop minimum is now documented in `docs/architecture/desktop-viewport-contract.md`: target `1440×900`, supported minimum `1280×720`, best-effort below that. Keep the graceful-degradation rules in sync with the code: the top nav scrolls horizontally when narrow, menus cap height and scroll when short, the status-chip rail scrolls horizontally instead of overflowing, panel interiors remain scrollable, and Stage mode stays the preview-first escape hatch.

### State Layer

**`src/state/graphStore.ts`** owns the React Flow node/edge arrays and wraps `applyNodeChanges`, `applyEdgeChanges`, `addEdge`. Also tracks `selectedNodeId` and exposes `updateNodeProperty`. The `onConnect` action embeds `style: { stroke: color }` on new edges so the MiniMap can pick up per-category edge colors.

It is a **multi-graph workspace** (ADR 0001): the *active* graph stays in the top-level `nodes`/`edges` (so all consumers are unchanged), while inactive graphs (pattern groups) live in `graphData`, keyed by id, with metadata in `graphs`. `createGroup` encapsulates selected nodes into a new subgraph (adding a `GroupOutput` terminal) and replaces them with a single `Group` node; `enterGraph` switches the active graph (pausing undo tracking around the swap and swapping in that graph's own history — each graph's zundo stacks are stashed in `stashedHistory` on the way out and restored on the way back in, so stepping into a group no longer discards the parent's undo stack, while a step recorded in one graph is never applied to another; `historyNodeLists()` counts stashed stacks as live references so the orphan sweep can't collect a subgraph an undo step still needs, and `loadGraph` clears the stashes). Scene-level singletons in the selection (`GROUP_EXCLUDED_TYPES` — `MatrixOutput`, `MicInput`, `MusicLibrary`) are **left behind** in the parent graph rather than sealed inside the group: a left-behind `MatrixOutput` becomes an outgoing boundary edge auto-rewired to the new `Group`'s frame output, and a left-behind source feeding the selection becomes an exposed `Group` input — so "select-all → group → repeat" keeps the output and sources in place for the next pattern. `getGroupRegistry()` assembles the `{ groupId: { nodes, edges } }` map that `evaluateGraph` needs, and `LEDPreview` passes it every frame so groups preview live at both tiers.

**Pattern library (Phase 1 of the generative-pattern-show workflow — see `docs/development/design/generative-pattern-show.md`).** `src/state/patternLibrary.ts` is a Zustand store of saved pattern groups cached in `localStorage` and mirrored as shareable JSON files in the repo-root `My Patterns/` folder (`usePatternLibrary`: `savePattern`/`renamePattern`/`deletePattern`). When the helper is online the folder is authoritative, so deleting a JSON file is a real deletion; a small local sync journal retries only unacknowledged saves/deletes instead of recreating every browser-only cache entry. A Group node's context menu **"Save to Library"** stores its port signature + subgraph; the Sidebar's **Pattern Library** lists them. Single-click selects, Ctrl/Cmd-click toggles, Shift-click selects the visible range, double-click or Enter drops a copy via `graphStore.instantiatePattern`, and drag still places a copy or adds it directly to a collection. The multi-selection context menu adds to the canvas, an existing/new collection, or bulk-deletes editable patterns. **Pattern Insights** live in `usePatternRatingStore`: Studio assigns an opinionated 0–100 score against an inferred or manually selected intent (`ambient`/`showpiece`/`accent`/`audio-reactive`/`static-utility`), while the user's persistent 1–5 stars remain independent. Analyses are cached by scoring version + graph content + nested groups + render dimensions; rename/shelf changes do not invalidate them. Library rows show both signals, and the collection picker can sort/filter by Studio Score, personal rating, and intent. The library also mounts 40 immutable curated beta patterns across two built-in shelves — 20 under **Standard** (`STANDARD_BUNDLED_PATTERNS`) and 20 under **Audio Reactive** (`AUDIO_BUNDLED_PATTERNS`), combined as `BUNDLED_PATTERNS` in `bundledPatterns.ts` — and lets users create/remove custom shelves; new saves start in **New & Unsorted** and can be dragged between shelves.

**Pattern Collection (Phase 2).** The `PatternCollection` node holds a chosen subset of pattern groups for a show. Its **Add patterns…** control opens a searchable saved-pattern manifest with name/shelf/rating sorting, multi-select checkboxes, existing-pattern detection, and a fixed action footer; `graphStore.addPatternsToCollection` clones a whole selection into the collection in one undoable state update. Wiring a **Group** node's frame output into its `pattern` input is still intercepted in `NodeGraphCanvas.handleConnect`: instead of creating a noodle it confirms and **absorbs** the group via `graphStore.addToCollection` — the Group node (and its edges) leave the canvas while its subgraph stays in `graphData`, and its id is appended to the collection's `properties.patternIds`. Saved patterns can also be dragged directly onto a collection. `PatternCollectionBody` renders the absorbed list (removable via `removeFromCollection`, which also drops the subgraph). The node outputs a `patternset` (the group-id list); the evaluator returns it from the `PatternCollection` case for the Pattern Master to resolve via the group registry.

**Pattern Master (Phase 3) — the generative show engine.** `PatternMaster` was repurposed from the old 4-input cycler into the show engine: inputs are a `patternset` + optional `transitions` (a `transitionset` from a wired `TransitionSet` node, the same one the `PerformanceGenerator` uses) + optional `beat`; properties are `minTime`/`maxTime`/`transitionSec` (inline sliders) plus the beat-triggered particle overlay (`particles`/`particleStyle`/`particleHue`/`particleIntensity`). The evaluator's `PatternMaster` case rasterises each collected pattern by recursing into its group (`evaluateGraph`, namespaced per pattern) and drives `evalPatternShow` — a stateful machine (module-level `patternShowState`) that holds a random pattern for a random dwell in `[minTime, maxTime]`, then transitions (a random style from the wired pool, or a plain crossfade when nothing is wired) into another random pattern; a wired `beat` advances early once `minTime` has elapsed and also fires a particle burst (`renderParticleBurst`, shared with the show preview). The 16 transition effects are shared with the `Transition` node through the extracted `compositeTransition(type, a, b, t, W, H, opts)`. `patternset` is a new port `dataType` (a `string[]` of group ids in `PortValue`). `validateGraph` warns when no collection is wired.

**Show codegen (Phase 4).** `src/codegen/showGenerator.ts` (`isPatternShow`/`generateShowSketch`) turns a `PatternCollection → PatternMaster → MatrixOutput` graph into a **controller sketch**: one `render_pN(uint32_t ms)` per collected pattern plus a `loop()` that holds a random pattern for a random dwell and crossfades into another (the firmware mirror of `evalPatternShow`). Each pattern body is produced by **reusing `generateCpp`** on the pattern's subgraph (re-terminated at a synthetic `MatrixOutput`) and rewriting the loop into a function — buffers prefixed per pattern, helpers hoisted/deduped — so every supported node type works in a show with no extra codegen. `MatrixOutputUpload` uses `generateShowSketch` when `isPatternShow`, else `generateCpp`. The full transition pool (all 16 styles, drawn from a wired `TransitionSet` via `SHOW_TRANSITIONS`) and the `beat` trigger (a wired `MicInput` supplies `_audioBeat`, gating early advance + the particle overlay) are implemented, mirroring the Phase 3 preview. Three things are trimmed rather than emitted unreachable: palette globals are narrowed to the `paldef_*` symbols the finished pattern bodies actually name (all 29 were declared before, ~1.4KB of dead `.bss` that PSRAM cannot offload); `compositeTransition` is narrowed to the baked `TRANS_POOL` (the crossfade `default:` arm always survives, so a pool of `{ 0 }` — the default with no `TransitionSet` wired — no longer compiles in fifteen unreachable effects); and a **one-pattern collection** omits `showA`/`showB`, the pool, and the compositing switch altogether, since the `PATTERN_COUNT > 1` guard meant they could never run. `transitionHelperCpp(styleIds)` does the narrowing; the music-sync player calls it with no argument because it selects styles from the `.show` file at runtime and can be handed any of them. Single-file output remains the only simplification: `isPatternShow` requires the `PatternMaster`'s `frame` output to actually reach a `MatrixOutput` (a disconnected `PatternMaster` never hijacks a normal sketch export), so multi-file `.h`-per-pattern output is the one remaining follow-up. **Hardware-validated** on an ESP32-S3 (16×16 WS2812B matrix, serpentine) via `fbuild` (2026-06-26): a two-pattern collection compiled (51% flash, 9% RAM) and ran with smooth crossfades and ~5 s dwell matching the preview. The beat trigger, non-crossfade transitions, and particle overlay were subsequently **hardware-validated** on an ESP32-S3 + INMP441 (2026-07-24, GitHub issue #106): a generative show with the on-device microphone ran a full cycle with beat-triggered early advance and the particle overlay behaving as configured. **On-device mic audio:** if a `MicInput` node is on the canvas, `generateShowSketch` hosts FastLED's shared INMP441 `fl::audio::Processor` (`audioEngineForGraph()` in `cppGenerator.ts`) and polls its normalized bands, equalizer, beat, and BPM into the established `_audio*` globals once per frame. Pattern subgraphs compile with external native-FastLED audio enabled, so their `FFTAnalyzer` and `BeatDetect` nodes consume the controller's processor output without creating another input or FFT. The separate SD player continues to supply the same globals from its baked song envelope and does not instantiate this live processor.

**`src/state/uiStore.ts`** owns workbench presentation: sidebar/preview visibility and widths (`sidebarOpen`/`previewPanelOpen`, `sidebarWidth`/`previewWidth`, `layoutPreset`), persisted `graphHealthOpen`, evaluation/Stage/Perform state, preview route/style/3D mode, status text/level, FPS and memory telemetry, theme, reduced motion, and high contrast. Upload/setup overlays live in `uploadStore.ts`, not `uiStore`. `performanceMode` is deliberately session-only and always starts false, matching Stage mode rather than the persisted appearance preferences. `setStatus` auto-clears any transient level (`info`/`success`/`error`) back to idle after 5 s, cancelling any prior pending timer so a newer message isn't wiped by a stale one. Every persisted preference writes through the guarded `save()` helper rather than a bare `localStorage.setItem` — these writes happen before the matching `set()`, so an unguarded throw on full or unavailable storage used to abort the action and leave the preference unapplied.

**Stage is the audience view.** The two idle seconds that hide the cursor also take every piece of chrome with them: `uiStore.stageIdle` (session-only, always false outside Stage, like `performanceMode`) is published by `App.tsx`'s pointer-idle effect and `LEDPreview` fades the header, telemetry, spectrum and transport out against it, leaving lit LEDs and nothing else. Pointer movement brings it all straight back, and hidden chrome is `inert` so a faded Exit button cannot be tabbed to or clicked through. The standby HUD deliberately stays — it is the only thing that explains a black stage. In-graph previews answer "what is *this* output showing"; the preview panel answers "what does the audience see".

**Screensaver / fullscreen Stage.** `enterStagePresentation()` (`src/utils/stagePresentation.ts`) enters Stage and requests browser fullscreen in the same click/F10 call stack so transient user activation is preserved; a rejected or unsupported request leaves a labelled windowed Stage rather than failing the mode. `App.tsx` mirrors browser-native fullscreen exit back into `stageMode`, holds a Screen Wake Lock while Stage is visible (reacquiring after tab visibility returns), and hides the cursor after two idle seconds. Stage hides the workbench menu/status chrome and provides its own exit control. The preview keeps the authored matrix aspect ratio and uses fit/letterbox sizing — it never crops, stretches, or increases evaluator grid dimensions.

**Graph Health inspector.** `GraphHealthDrawer` is an always-available workbench drawer below the editing canvas (hidden in Stage mode). It continuously derives structured, node-attributed diagnostics through `buildGraphDiagnostics` in `src/utils/validateGraph.ts`, covering incomplete wiring, expressions, pin conflicts, preview-only nodes, output power, internal RAM, show structure, and selected-board compatibility for either the main graph or an entered group. Every diagnostic includes concrete repair guidance; node issues select and fit the affected nodes, while workspace issues can open the node library or board chooser. Keep deployment validation and these live diagnostics backed by the same validation helpers so their rules do not drift.

**LED output forms.** `MatrixOutput` (labelled per form, so the node header reads **LED String** / **LED Matrix** / **LED Ring** / **HUB75 Panel**) is the single node for every LED output, selected by a `form` property — the pattern `Noise`/`Transition`/`Blend`/`Particles` already follow, since all four share a port signature. `src/state/ledOutputForm.ts` is the one place that answers what an output physically is, and LED count, composition footprint, which inline editors are enabled, and which validation runs all follow from it: `outputForm`, `outputLedTotal`, `outputGridDims`, `outputCanvasDims`, `ringSampleMap`. `form` replaced two properties that answered the question by accident — `chipset === 'HUB75'` meant "scan panel" while pretending to name a wire protocol, and the short-lived `LedStringOutput` node type meant "a run of tape" while having no `case` in `cppGenerator.ts` at all (a string-only graph compiled to a "not yet supported" comment; folding it in as `form: 'strip'` is what gave it firmware). `layout: 'strip'` is deliberately **not** read as the strip form — `xyLayout` always treated it identically to `'matrix'`, so it only ever meant "this grid is wired as one continuous chain", and reading it otherwise turns a saved 16×4 panel into a 60-LED run. `ledHardwareFromProps` derives `chipset: 'HUB75'` from the form, so a stale chipset string can never flash a panel as WS2812B; the chipset dropdown offers `ADDRESSABLE_CHIPSET_OPTIONS` (no HUB75) while sanitisation still accepts the full `CHIPSET_OPTIONS` for saved graphs. The hardware pane offers four **Add Hardware** entries, one per form, each creating the node pre-set with a size that suits it; a HUB75 panel takes its own signal ribbon rather than an LED data pin, so it stays available when the board is out of GPIO.

**The ring form.** A ring's LEDs are one chain like a strip's, so its route grid is 1×N — but it reads a *circle* out of the composition rather than a line, and that mapping is the whole difference between the two. `ringSampleMap(ledCount, startAngle, direction, canvasW, canvasH)` returns one row-major canvas index per LED in wire order, measured from 12 o'clock (where a ring's data-in pad usually sits) with `cw` running the way a clock does seen from the front. The live preview routes through it (`routeFrame`), the hardware view and the in-graph preview paint through it, and `cppGenerator.ts` bakes it as `const uint16_t _ringmap[RING_LEDS] PROGMEM` — one pure helper, so the circle on the bench and the circle on screen cannot drift. Two things are easy to get wrong here: (1) a ring claims a **square** composition footprint (`outputCanvasDims`, diameter `N / π` so roughly one canvas pixel sits under each LED) rather than a strip's 1-pixel-tall one, because a circle cannot be sampled out of a single row; (2) the map's indices are into the **composition** canvas, which a route does not know — a ring beside a bigger matrix reads that larger canvas — so `ringMapFor(route, canvasW, canvasH)` builds it against the canvas that actually exists and caches by geometry, and baking one at `outputRoutes` time silently lights every LED from the wrong pixel. Firmware sizes `leds[RING_LEDS]` from the physical count while `NUM_LEDS` stays the render resolution, the same split supersampling already uses.

**Runs wired in parallel.** Two LED outputs fed the *same frame* and assigned the *same data pin* are one controller with both runs' data lines on that GPIO — the "two identical panels showing the same thing" case. `outputMirrorLeaders` (`outputRouting.ts`) maps each route to the run that owns the controller; a route that maps to itself is a leader, a route that maps to another is a mirror and gets no `leds` array, no `addLeds`, and no blit, because the pixels reach it down the leader's wire. `graphStore.onConnect` makes this the default: wiring a frame into a second output adopts the first's pin (`withAdoptedMirrorPin`), since allocating a fresh GPIO made the app disagree with the bench and then raised a pin conflict when the user wired it truthfully. Editing the pin afterwards splits them into two independent runs again, which is also real and stays supported. Deliberately not grouped: a HUB75 panel (signal ribbon, no data pin to share) and same-frame outputs on *different* pins. Three asymmetries matter and are easy to get backwards — **power counts every physical run** (two panels are two panels on the PSU; counting the shared array once would under-read the draw by half in exactly the brownout case), **RAM counts the array once**, and a mirror **does not size the composition canvas** (nothing renders at its size). `findMirroredOutputMismatches` reports a mirror of a different length as a **warning, never an error** — the shorter run takes a prefix of the longer one's pixels, which is a real build (eight strips forming a star with four of them half length) rather than a misconfiguration, so it must not block an upload. Both pin-collision walks — `findPinConflicts` for deploy and `buildGraphDiagnostics` for the Graph Health drawer — read the shared `deliberatelySharedPinUses` helper; they are separate loops over the same data and drifted once already, leaving the drawer calling a deliberately shared pin an error after deploy validation had stopped.

**Multi-output routing.** `MatrixOutput` is no longer a singleton: every instance is an explicit Frame route with independent controller pins, chipset/color order, size, layout, and brightness. `src/state/outputRouting.ts` defines the shared composition canvas (largest route, including supersampling) and the `fit`/wrapped-`crop` mapping used by preview and `cppGenerator.ts`; generated normal sketches allocate one physical LED array per route and call `FastLED.show()` once after all routes are populated. GPIO validation covers all outputs and other hardware nodes together, while layout/power/RAM checks cover every route. See `docs/architecture/multi-output-routing.md`.

**Menu-bar chrome.** `src/components/MenuBar/MenuBar.tsx` now keeps the top-level strip focused on workflow actions — File, undo/redo, Tidy, Start, Perform, Stage, preview style, and Mic stay directly clickable — while a compact **View** menu carries the less frequently changed appearance/preferences toggles (`Theme`, `Motion`, `Contrast`, `UI FX`, and `Signal dimming`). Signal dimming defaults off so selecting a node does not unexpectedly hush the rest of a new user's graph; an explicit toggle is still persisted. The View menu items render the current state inline (for example `Theme: Dark`, `Motion: Reduced`) so moving them off the bar does not hide what mode the app is in.

**`src/state/audioStore.ts`** is a thin Zustand bridge over `AudioEngine.instance`. It calls `engine.subscribe()` at store-creation time so FFT data flows into Zustand state on every animation frame.

**`src/state/projectStore.ts`** owns the named-project switcher: each project is a full persisted workspace (`nodes`/`edges` plus `graphData`/`graphs`/`activeGraphId`) with `createdAt`/`updatedAt` metadata, plus an optional per-project upload target (`uploadTarget`: remembered `selectedFqbn` + `selectedPort`). Projects are cached in localStorage under `design-studio-for-fastled.projects.v1` and write-through synced to helper-backed JSON files in the repo-root `Projects/` folder when the backend is available. `App.tsx` now autosaves into the **current project** rather than a single global slot, migrating the old `design-studio-for-fastled-graph` autosave key into the default `Main` project on first load; the File menu's **Manage Projects…** item opens `ProjectsPopup`, the UI for creating, duplicating, switching, renaming, and deleting projects (the File menu itself carries New / Open Project File / Save / Save As plus the six most recent projects). The menu-bar brand subtitle names the current project and is a second way into that popup; with no project open it turns into a red `No project — not saving` warning, since `saveCurrentWorkspace` genuinely no-ops in that state (the rolling recovery snapshots keep running regardless).

Disk is authoritative for a project the helper has confirmed it wrote, but — exactly like the pattern library — a **sync journal** (`design-studio-for-fastled.projects-sync.v1`) records every write/delete until the helper acknowledges it. `reconcileProjectsFromDisk` keeps journalled-unsynced projects and suppresses journalled-undeleted ones, so a browser-only session (helper never installed, every `saveProjectToDisk` silently failing) does not lose every project the first time a helper comes online and reports an empty `Projects/` folder. `refreshFromDisk` replays the journal — deletes first, then writes, folding a successful retry back into the already-fetched disk snapshot — before reconciling.

**Project-change prompts** run through `uiStore.requestNewProjectDecision(...)` and `NewProjectPrompt`: the user-facing actions are explicit (`Save and continue`, `Continue without saving`, `Cancel`), and the prompt state carries both the current project name and a destination label (for example `project "Show A"` or `a new blank project`). `MenuBar` defers the prompt for project-file opens until after the target file/project name is known, so the dialog can name the actual destination instead of a vague "another project".

**Project vocabulary.** Keep the nouns consistent in UI copy and docs: **Project** = the everyday autosaved working workspace; **Project File** = a portable full-workspace file opened with `Open Project File` or written with `Save Project File As`; **Graph JSON** = raw graph interchange via `Import Graph JSON` / `Export Graph JSON`; **Share Link** = a URL containing the full workspace; **Recovery Snapshot** = one of the recent browser-local restore points exposed by `Recover Snapshot`. When one of those actions replaces the canvas contents, refer to it as the **current project workspace** so the user can tell whether they are replacing the live project, importing interchange data, or restoring a recovery point.

**Starter templates** live in `src/state/starterTemplates.ts` and are loaded through the persistent **✦ Start** button / `TemplatesPopup` start gallery or directly from the empty-canvas start screen in `NodeGraphCanvas`: Rainbow Sweep, Fire, Scrolling Text, Audio Spectrum, Field Warp Demo, plus two separate show starters — **Generative Show** (`Pattern Collection → Show Engine → Matrix Output`) and **Music-synced SD Show** (`Music Library → Performance Generator → SD Card → Matrix Output.sdcard`). Each template carries concrete completion steps and one editable tutorial `Comment` on the loaded canvas (omitted from the tiny gallery graph preview); the Audio Spectrum starter also disables the synthetic test signal and requests the live microphone. The gallery renders thumbnail graph previews, and `uiStore.lastStartChoice` remembers the user's most recent starter (including `Blank Canvas`) without hiding the rest of the gallery. `src/utils/startFlow.ts` is the shared launch path: it loads the chosen graph, clears undo history, records the remembered choice, and requests a fit-view so the freshly-started patch lands framed on screen immediately.

**`src/state/nodeLibrary.ts`** is the static registry (`NODE_LIBRARY: NodeDefinition[]`). Adding a new node type = add one entry here. No other registration required — the Sidebar reads this array directly.

**Sidebar progressive disclosure.** `src/components/Sidebar/Sidebar.tsx` now treats the node library as a guided rack rather than a flat dump: it defaults to **All** so the complete library is visible, offers a curated **Beginner** subset, remembers the chosen scope plus per-user `favorites` and `recent` nodes in `localStorage`, adds small intent tags to cards for search/discovery, and surfaces a `Quick recipes` shelf that drops three real-audio starter chains — `Live spectrum`, `Beat colour jump`, and `Percussion trails` — straight onto the canvas with an editable tutorial `Comment`. Recipe drops disable and persistently clear the synthetic test signal, start the microphone, reuse scene singletons (`MicInput`, `MatrixOutput`) when present, and skip only the conflicting terminal wire when they need the user to finish connecting into an existing output path.

### Node Rendering

`StudioNode` (`src/components/Canvas/StudioNode.tsx`) is the single custom node type (`{ studioNode: StudioNode }`). **Critical invariant:** React Flow requires `Handle` components to be `position: absolute`. Handle `top` offsets are calculated from constants that must stay in sync with the CSS:

```ts
// StudioNode.tsx — must match StudioNode.module.css
const HEADER_H = 32   // .header height
const BODY_PAD = 8    // .body padding-top (--space-1)
const ROW_H    = 24   // .portRow height
const ROW_GAP  = 4    // .body gap
const PREVIEW_H = 40  // WaveScope .scope height (only on Wave/ComplexWave)
const handleTop = (i, previewOffset) => HEADER_H + BODY_PAD + previewOffset + i * (ROW_H + ROW_GAP) + ROW_H / 2
```

Changing any of those CSS values without updating the constants will silently misalign all connection handles.

**Per-node live previews:** every node whose primary output is a `frame`, `palette`, or `color` shows a live preview at the top of its body (`NodePreview`): a mini LED-matrix thumbnail (canvas), a gradient strip, or a colour swatch respectively. Frame thumbnails fill the node width at the matrix aspect ratio — `StudioNode` computes the height (`BODY_CONTENT_W × gridH/gridW`, grid dims read from the MatrixOutput node) and feeds it to `NodePreview`; port handles stay aligned for free since each `.portRow` is its own flex row (the preview, wave scopes, and per-node bodies are just earlier siblings in the body's flex column, not an absolute-offset calculation). These are driven by a **single shared evaluation pass**: `LEDPreview`'s render loop calls `evaluateGraphFull` (which returns the terminal frame *and* every node's output ports in one `createEvalNode` pass, so stateful nodes aren't double-advanced) and publishes the per-node outputs to `previewStore` on every evaluated frame — the same ~60fps wall-clock cadence as the main canvas; each `NodePreview` subscribes to its node's entry. A small **▾/▸ toggle button** overlaid on each preview (`previewHidden` in the node's properties, excluded from the generic property list) collapses it to a slim "▸ preview" strip, for quieting a busy graph node by node.

**Waveform preview scope:** `Wave` and `ComplexWave` nodes render a `WaveScope` mini-oscilloscope at the top of the body (above the port rows). Because handles are absolutely positioned, this scope pushes the rows down — so `handleTop` takes a `previewOffset` (`PREVIEW_H + ROW_GAP` for these nodes, else 0). `Wave`'s scope samples its own configured shape (`waveNodeSamples` in `src/state/wave.ts`, which also backs the evaluator). `ComplexWave`'s scope (`ComplexWaveScope`) is **live**: it subscribes to `nodes`/`edges` and samples the node's own `result` port across the window via `evaluateScalar`, so it reflects the actual upstream inputs and the chosen operation.

`evaluateScalar(nodes, edges, nodeId, portId, tick)` probes a single node's scalar output by reusing the shared `createEvalNode` core (the same machinery `evaluateGraph` runs), so a probe matches what the graph actually computes. It runs under a reserved `__scope__/` state namespace so stateful upstream nodes don't disturb the live render.

**Typed port colours:** each handle (input/output dot) is tinted by its port `dataType` via `portColor()` (`nodeLibrary.ts`), so ports that can connect share a colour — `float`/`bool` share grey `#9aa0a6` (they interconvert per `portsCompatible`, also in `nodeLibrary.ts` and shared by the canvas + picker); `color` `#ffd24a`, `palette` `#ff5cf0`, `image` `#c6a0ff`, `frame` `#5ad1ff`, `field` `#f5c542`, `audio` `#00e0a4`, `songs` `#ffb74d`, `shows` `#ffa726`, `sdcard` `#ffa500`, `patternset` `#00e0a4` are each distinct. The node header/border still uses the category accent. Handles also carry a `label · dataType` title.

**Drag-to-create:** dropping a noodle dragged from an **output** onto empty canvas opens the `CanvasContextMenu` picker pre-filtered to nodes that have an input compatible with the dragged type, then auto-wires the chosen node to its first matching input. `onConnectStart` records the output's `{ nodeId, handleId, dataType }` in a `connectFrom` ref; `onConnectEnd` opens the picker only when the drop has no end handle (`!state.toHandle`). `CanvasContextMenu` takes an optional `connectFrom` prop that puts it straight into picker mode, ranks compatible nodes by fit (exact-handle matches, `spliceInput`, FFT three-band fan-out, same-type pass-through), shows each card with the node description plus a short “why this fits” hint, and still calls `onConnect` after `addNode`. When there is no obvious direct target — or when the user wants to jump across data types faster — the same picker also exposes prewired bridge chains such as `Audio → frame`, `Audio → color`, `Color → frame`, `Frame → field`, `Field → frame`, `Music → SD card`, and `Shows → SD card`, instantiating the whole helper chain from one click.

**Drop-to-splice + auto-spread:** when a node dragged from the sidebar is dropped onto an existing noodle (`onDrop` in `NodeGraphCanvas`, within `SPLICE_DIST` flow units of the edge segment, via `distToSegment`) and the node has an input compatible with the edge's source output *and* an output compatible with the edge's target input (`portsCompatible`), it's spliced in: `graphStore.insertNodeOnEdge` drops the old edge and wires `source → new → target` (matching `onConnect`'s glow/reconnect style). Otherwise the node just lands where dropped. To keep the area tidy, `spreadNodes` (run after a splice, after every `onConnect`, and on `onNodeDragStop`) walks edges left-to-right and shifts any target that *crowds* its source rightward (grid-snapped) to restore `MIN_NODE_GAP`. "Crowds" means too close horizontally **and** overlapping vertically, so a pair deliberately stacked in a column (a long noodle dropping straight down) is left alone; it only ever pushes right, so it spreads a cramped chain without disturbing a layout that already has room.

**Tidy graph (auto-arrange):** the menu bar's **▦ Tidy** button (also "Tidy Graph" in the canvas context menu) runs a layered Sugiyama-style layout over the active graph — or just the selection when 2+ nodes are selected. `src/utils/tidyLayout.ts` (pure, unit-tested) assigns each node a column by longest path from a source (sources are then pulled right next to their first consumer), orders rows by barycenter sweeps over the evolving y-centres, anchors the result to the scope's current top-left, and snaps to the 20px grid; isolated nodes are left where the user put them (unless they'd obscure the tidied graph, in which case they're parked in a row beneath it), and the layout is **idempotent** (each column re-centres on its mean desired centre after stacking, so a second Tidy is a no-op). `src/utils/tidyGraph.ts` (`runTidy`) glides nodes over ~200 ms (instant under reduced motion; a `setTimeout` watchdog lands the layout even when rAF is suspended in a background tab) and records the whole tidy as a **single undo step** — the pre-tidy graph is pushed onto zundo's `pastStates` manually and tracking stays paused during the animation. `spreadNodes` remains the quiet incremental nudge; Tidy is the full reset.

**Inline property editors:** the node body renders editable controls for each property, Blender-style — so editing happens on the node with live preview. Control choice: a colour swatch for `r/g/b`; then by `propertyMeta(nodeType, key)` (`nodeLibrary.ts`) — `select` dropdowns for enum properties (`palette`/`paletteA`/`paletteB`, `direction`, `mode`, `chipset`, `colorOrder`) and `slider` (range + value readout) for bounded numerics (`speed`, `scale`, `fade`, `amount`, `count`, `kelvin`, …); otherwise type-based fallbacks (checkbox for booleans, number/text field). Add a `PROPERTY_META` entry to give a property a dropdown or slider — keyed by **property name** (shared across nodes), so for a name that means something different on another node (e.g. `speed`/`scale` are normalised 0–1 sliders on the pattern nodes but a steps/sec rate on `GameOfLife`/`ReactionDiffusion`; `rate` is 0–1 on `Particles` but degrees/sec on `Transform`) add a `PROPERTY_META_OVERRIDES[nodeType]` entry instead (the shared `const N01` is the standard 0–1 slider).

**Normalised speed/scale (0–1):** the `speed`/`scale` sliders on the pattern nodes are a uniform **0–1**; `src/state/speedRange.ts` maps each 0–1 value onto that node's internal animation rate (`SPEED_MAX`/`SCALE_MAX` per node type; the bundled `Noise` node re-tunes per `noiseType` via `NOISE_SPEED_MAX`/`NOISE_SCALE_MAX`). Both the evaluator (`denormRate`) and the C++ generator (`rateCpp`) apply it, so one slider spans the useful range and preview matches firmware. This mirrors `src/state/audioFlowRange.ts`, which does the same for the `AudioFlow` node. The audio-reactivity knob on the spectral nodes is `energy` (0–1, formerly `intensity`); `Counter`'s control is `rate` (0–5, formerly `speed`). These render in a `.props` section **below** the port rows, so they don't affect the handle offsets above. Interactive controls carry the `nodrag` (and `nowheel` for number fields) class so React Flow doesn't pan/drag while editing. Structured objects such as `font` are excluded from the generic inline property list; the legacy `Inspector` component remains in source/tests for that specialized authoring UI, but it is not mounted in the current workbench and `uiStore` has no inspector toggle.

**Per-input clamping:** any node with a bounded float input shows a `clamp inputs` checkbox (`props.clampInputs`, rendered specially in `StudioNode` via `hasClampableInputs()`). When on, a *wired* float input is clamped to its slider's `[min, max]` (`inputClampRange()`) — the inline alternative to wiring a `Clamp` node onto every connection (an unwired value already comes from a bounded slider, so only wired signals are clamped). Both the evaluator (`num()`) and the C++ generator (`floatExpr` → `constrain(...)`) honour it, so firmware matches the preview.

**Node bypass:** any node whose primary output is `frame` or `field` and has a matching-type input (effect-chain nodes like `Blend`/`Blur2D`/`FieldRotate`/…) shows a `bypass` checkbox (`props.bypassed`, gated by `bypassPort()` in `nodeLibrary.ts`, which picks the pass-through port pair). When on, the node's own logic is skipped entirely: the evaluator (`evalNode`) returns the matching input value as the output with no side effects, and the C++ generator (`emit`) copies the source buffer into the node's own (`memmove` for `frame`, `memcpy` for `field`) instead of emitting its render — a quick A/B mute for an effect in a chain, faster than unwiring/rewiring.

### Edge Rendering

`GlowEdge` (`src/components/Canvas/GlowEdge.tsx`) renders three stacked SVG `<path>` elements (wide halo → mid bloom → thin animated core) plus a dot at the target. Color is resolved at render time from `useReactFlow().getNode(source)?.data.category`. The MiniMap picks up edge colors from `style.stroke` set at connect time in `graphStore.onConnect`.

Edges ("noodles") can be unplugged from a node's **input** end two ways. (1) **Grab the input port dot directly** — `onConnectStart` detects a drag beginning on an already-connected `target` handle and immediately `removeEdge`s that noodle (a `detaching` ref), so the gesture becomes an unplug (drop on empty) or re-route (drop on a compatible output, which `handleConnect` re-adds) instead of starting a dead-end new wire. This is the primary path because React Flow's reconnect anchor sits in a thin strip just *outside* the port and is hard to hit. (2) Edges are also created `reconnectable: 'target'`, so the React Flow reconnect anchor still works: the canvas wires `onReconnectStart`/`onReconnect`/`onReconnectEnd` and a `reconnectLanded` ref deletes the edge if the dragged end lands on empty space (`removeEdge`) or re-routes it (`reconnectNoodle`).

### Live Preview Pipeline

`LEDPreview.tsx` drives a `requestAnimationFrame` loop that evaluates the graph (`evaluateGraphFull`, see per-node previews above) and renders the matrix. **Timing is wall-clock based:** the loop gates to ~60 steps/sec off `performance.now()` and passes `tick = elapsedMs / (1000/60)` so `t = tick/60` equals real seconds — matching the firmware's `millis()/1000`. This means animation speed is independent of the display refresh rate (a 120 Hz panel would otherwise run everything ~2× fast, since the old code incremented `tick` once per rAF assuming exactly 60 fps). When the graph is empty, `idleFrame()` shows a rainbow shimmer instead. The per-frame body is wrapped in `try/catch` so a single malformed frame logs and is skipped rather than tearing down the loop.

**`src/state/graphEvaluator.ts`** is the runtime engine. It topologically evaluates nodes in dependency order using memoisation per frame. Key types:

```ts
export interface RGB { r: number; g: number; b: number }
export type Frame = RGB[][]   // row-major [y][x]
```

Stateful nodes (`Fire`, `Fire2012`, `BeatFlash`, `Counter`, `Particles`, `PatternMaster`, `ReactionDiffusion`, `GameOfLife`, `FlowField`, `Starfield`) persist state in module-level `Map` objects keyed by `stateKey(id)` — the node id prefixed with the group-instance path, so two instances of the same group don't share state. `formulaCache` parses `CustomFormula` expressions once through the closed expression language in `formulaLang.ts`; do not reintroduce `new Function` or other ambient-JavaScript evaluation.

`evalNode()` guards against graph cycles with an `inProgress` set: re-entering a node still on the evaluation stack returns `{}`, so the upstream input falls back to its default instead of recursing into a stack overflow. Keep this guard in place when editing the evaluator.

**Preview trust boundary.** Imported/share-linked/project-file content and newly dropped library patterns are untrusted until the user explicitly chooses **Trust and run**. The active workspace's `trusted` flag must reach every evaluator entry point: the main `LEDPreview` pass and music-sync collection playback (`renderShowFrame`, including node-local playback, preview baking, and the main-preview override). It must also reach every **recursive** call — `evaluateGraph`'s `Group` case and `PatternMaster`'s per-pattern `render` helper both re-enter `evaluateGraph` for a subgraph, and both forward `trusted`; since it is the last positional parameter and defaults to `true`, a call that stops one argument short silently laundered nested content past the gate (fixed 2026-08-03), which is exactly the shape a shared pattern takes. While untrusted, `CustomFormula`/`FieldFormula` return blank data and `Code` returns a black frame; baked collection frames are not reused. Formula parsing stays inside `formulaLang.ts`'s fixed identifier/function set, and Code preview execution stays inside the terminate-on-timeout worker in `codeSandboxRuntime.ts`/`codeSandbox.worker.ts`.

**The warning is content-aware; the flag is not.** A workspace loaded from outside is always untrusted, but `TrustBanner` and `promptTrustIfNeeded` only *say* so when `workspaceTrustHolds` (`patternTrust.ts`) finds something the flag actually blocks — a `CustomFormula`/`FieldFormula`/`Code` node anywhere in `nodes` or `graphData`, or an Art-Net-mode `DMXInput` — and the copy names only what is held. Before 2026-08-14 both warned unconditionally, so an ordinary shared `Plasma → Matrix Output` graph described a block that wasn't happening, which is how a security affordance teaches people to dismiss it. The gate itself is unchanged: the workspace stays untrusted, the banner appears the moment gated content is added, and export/upload confirms separately. `workspaceTrustHolds` is deliberately a *superset* of `patternNeedsTrust`'s `TRUST_GATED_NODE_TYPES` and deliberately a separate list — the pattern critic renders saved subgraphs without mounting node bodies, so a pattern's `DMXInput` can never open a socket and must not interrupt a scan. Merging the two lists reintroduces a prompt the pattern path has no reason to show.

**The trust flag is not the whole boundary — two surfaces sit outside the evaluator.** (1) **Codegen must validate formula source itself.** `cppGenerator.ts` pastes a formula into `float _v=<formula>;`, so it calls `isNodeFormulaValid` (`formulaLang.ts`) and falls back to `0.0f` when the sandboxed parser rejects the string; `findFormulaErrors` (`validateGraph.ts`) blocks export/upload and raises a Graph Health diagnostic for the same case. Until 2026-08-14 codegen skipped this entirely, so a shared graph could smuggle arbitrary C++ through a formula property into a flashed sketch — the browser guarantee existed only in the browser. The parser is what makes the paste safe: its tokenizer has no token for `;`, `{`, `}`, quotes or `#`, so a formula that parses cannot carry a statement. Any *new* codegen path that interpolates a user string into emitted C++ needs the same treatment — echo a value resolved against a known set rather than the raw property (see the `FormulaPoints` attractor preset, where a newline in the raw name would have ended a `//` comment). (2) **Node bodies that perform I/O on mount must gate on `trusted` themselves.** `DmxInputBody` opens the helper's Art-Net UDP listener on a port carried in the node's own `previewPort` property; it now holds that listener closed until the workspace is trusted and says so on the node. The socket deliberately still binds `0.0.0.0` once trusted — Art-Net arrives from consoles on the LAN, so localhost-only would break the feature; consent, not the bind address, is the control.

**Pattern Insights trust gate.** The Studio critic (`patternRating.ts`) renders a saved pattern's subgraph on its own, outside any workspace, so there is no workspace `trusted` flag to consult — it resolves trust per pattern instead. Bundled curated patterns are trusted by definition; anything else is checked against `patternTrust.ts`'s content-addressed store (the same one `TrustBanner`'s "Trust and run" writes to). Scans start only from the explicit **Scan patterns** action. When the pattern is untrusted **and** running it would actually execute gated logic — `patternNeedsTrust()` looks for a `CustomFormula`/`FieldFormula`/`Code` node in the subgraph *or in any nested group* — `promptPatternTrust` (`utils/trustPrompt.ts`) asks **Trust and rate** vs. **Skip this pattern**. A yes is remembered by content; a no returns a `skipped: true` result that is deliberately not reusable, so a later scan asks again. `captureWindows` takes the resolved trust value rather than hardcoding `true`, and concurrent asks for the same pattern share one dialog.

**Groups (ADR 0001):** `evaluateGraph(nodes, edges, tick, W, H, groups)` takes an optional group registry. A `Group` node recurses into `groups[groupId]` (a subgraph) and returns the frame from that subgraph's `GroupOutput` terminal; a `groupStack` breaks group-level recursion. The `instancePrefix`/`groupStack` params are internal recursion bookkeeping — callers leave them defaulted.

A **3D view** toggle (`uiStore.preview3d`) wraps the canvas in a CSS `perspective` container and applies a drag-driven `rotateX/rotateY` to orbit the matrix panel — no Three.js or renderer changes; the canvas content is still drawn the same way each frame.

**Preview recording/export.** The preview header's **⏺ Record** button opens `RecordPopup` (`src/components/Preview/RecordPopup.tsx`): PNG snapshot, animated GIF, or WebM video with duration/FPS/scale/seamless-loop/warm-up options and a **Match preview** vs. **Flat pixels** style choice. `recordCapture.ts` renders clips **offline and deterministically** from t = 0 at the chosen capture fps by calling `evaluateGraph` under a per-capture `__record_N/` `instancePrefix` (the same state-isolation trick as `evaluateScalarSeries`/the show preview — the live preview's stateful nodes are untouched, and the abandoned namespace is reclaimed by the idle-TTL sweep); each frame is copied to packed RGB bytes immediately because evaluator frames are pooled. Its per-frame pipeline **mirrors `LEDPreview`'s render loop step for step** — evaluate on the shared composition canvas, `routeFrame` into the selected output, master brightness, idle-shimmer fallback, then `applyShowPlaybackSignal` (a PerformanceGenerator show overlaying the preview is recorded too, advanced on the capture clock from its current `posMs`). Frames are sized from the **route's own** width/height, never a clamped display dimension — the `Math.max(2, …)` that `RecordPopup` used to apply appended a phantom black row to every 1-row strip export. `warmupSec` renders and discards leading frames so simulations (Fire, Trails, Particles, Game of Life, Reaction-Diffusion) start settled rather than in their blank boot state; the UI offers a 2 s default. Between-chunk yields use a `MessageChannel` (timer callbacks are throttled in hidden tabs). Seamless loop renders extra tail frames and crossfades them over the clip's opening.

Rasterisation goes through **`recordRenderer.ts`**, whose `preview` mode drives the *same* renderers the on-screen matrix uses — `WebGLLEDRenderer` (constructed with `preserveDrawingBuffer: true` so each draw can be read back; the live preview leaves that off) falling back to `frameCanvas.ts`'s Canvas-2D path — at the live preview's effective style (`uiEffectsEnabled ? previewStyle : 'standard'`). Keeping one renderer for both surfaces is the point: the previous standalone LED-look rasteriser resolved a single source LED per output pixel, so it could not bloom across LED boundaries and silently ignored the diffused styles entirely. `recordRasterizer.ts` is now only `expandFlatFrame`, the exact-colour no-glow **Flat pixels** mode for documentation and bug reports. Because the diffused styles need Canvas-2D `filter` blurs and the standard look needs a WebGL shader — neither dependable on an OffscreenCanvas across browsers — rasterisation happens on the main thread and `gifEncoder.worker.ts` receives ready-made RGBA, owning only quantisation and LZW. `src/utils/gifEncoder.ts` is a zero-dependency GIF89a encoder (per-frame local colour tables, 5-bit posterize + median-cut quantisation when a frame exceeds 256 colours, GIF-variant LZW) unit-tested against a real decoder; WebM uses `canvas.captureStream` + `MediaRecorder` playing the pre-rendered frames back in real time. PNG snapshots the exact live frame via `latestStreamFrameCopy()` (`streamStore.ts`), falling back to a one-frame offline render. The Canvas-2D LED-disc renderer (`renderGridFrame`) and the diffused-style renderer (`renderDiffusionFrame`, plus the shared `renderPreviewFrame` entry point) both live in `frameCanvas.ts`; each caller owns its own `DiffusionScratch` pair, since the live preview and an in-flight export composite at different sizes.

**Live-audio capture for recordings.** The evaluator's audio cases read `useAudioStore.getState()` at evaluation time — correct at 60fps where evaluation *is* real time, but an offline capture renders far faster, so every frame would sample one frozen instant. `recordAudio.ts` fixes this the same way the SD show pipeline bakes an envelope, sourced from the mic instead of an offline song analysis: `recordAudioTimeline` listens on rAF for the clip's real duration (`total + loop-blend` frames), folding the store into one `AudioOverride` per capture frame, and `captureSequence` then replays that timeline through `evaluateGraph`'s `audioOverride`. `createAudioTimeline` is the pure, unit-tested core — it **latches `beat` across a bucket** so a beat that pulses for a single animation frame between two capture frames still lands in the clip, **clones the spectrum arrays** (the analysis engine reuses its buffers, so storing references would leave every snapshot aliasing the last sample), and carries levels forward across an unsampled bucket **without repeating its beat** (which would stutter one accent into two). The listen resolves once the duration elapses and the final bucket is filled, or after a bounded `LISTEN_GRACE_MS` — waiting unconditionally would hang the export whenever the capture fps runs ahead of rAF. Warm-up frames hold `timeline[0]`.

`AudioOverride` gained **`implicitConnection`** for this: an override normally *is* the audio source (a show's song, with no cable to draw), so `audioConnected` is true wherever one is supplied. The recorder replays the same mic the canvas is reading, so it sets the flag false and an unwired analysis node stays unwired — otherwise an export would light up nodes the preview leaves dark. It defaults to true, leaving every existing show/SD/pattern-rating caller unchanged. The dialog offers **Capture live audio** only when the graph consumes audio *and* input is actually running (`liveAudioAvailable()`); with the mic off it says so, since the evaluator's silent / test-signal fallbacks are already deterministic and listening would just add a wait for nothing.

**`src/components/Preview/webglRenderer.ts`** — `WebGLLEDRenderer` uploads the frame as a texture and renders via a GLSL fragment shader. The shader draws each LED as a smooth circular disc with a 5×5-neighbor glow contribution. Y is flipped in the shader (`u_res.y - gl_FragCoord.y`) to match the JS frame's top-left origin. Falls back to Canvas 2D if WebGL is unavailable.

### Audio Pipeline

`src/audio/audioEngine.ts` — `AudioEngine` (singleton) uses `getUserMedia` with a 44.1 kHz `AudioContext`; its `AnalyserNode` is only a time-domain sampler. `src/audio/fastledReactive.ts` ports FastLED 3.10.3's signal conditioner, frequency-band adaptive normalization, equalizer layout, and beat detector to TypeScript (using a 512-point Hann FFT with log-rebin approximations for FastLED's CQT kernels). It polls on every animation frame and publishes `{ bass, mids, treble, beat, bpm, spectrum, nativeFastLed }`. Shared capture constants and the browser FFT helper live in `src/audio/micAnalysis.ts`.

`src/state/audioStore.ts` bridges `AudioEngine` → Zustand. `FFTAnalyzer` and `BeatDetect` nodes in the evaluator read from `useAudioStore.getState()` directly (not through React).

**Audio-source contract:** the live `AudioEngine` is microphone-only. Playing a local track in the preview player must never attach its `<audio>` element to the engine or replace the MicInput signal; all ordinary live analysis nodes (`FFTAnalyzer`, `BeatDetect`, `PercussionDetect`, `AudioFeatures`) continue to read the physical microphone. The browser mic request explicitly disables echo cancellation, noise suppression, and browser automatic gain so same-machine playback is not treated differently from an external player; the MicInput gain maps to FastLED's `Processor::setGain`, while FastLED owns conditioning and adaptive normalization. Music Library analysis and generated-show playback are the separate source: `renderShowFrame` feeds collected patterns the song's baked analysis envelope through `audioOverride`, matching the exported hardware show. This baked/SD path deliberately retains Studio's tunable per-node BeatDetect and is not changed by the live FastLED integration.

App.tsx auto-starts audio when a `MicInput` node is added to the graph; auto-stops when it's removed.

**On-device audio (firmware).** The `MicInput` node carries the I2S pins for an **INMP441** MEMS mic (`i2sWs`/`i2sSck`/`i2sSd`, default 39/40/41, plus `channel` Left/Right). When present, `cppGenerator.ts` creates `fl::audio::Config::CreateInmp441(...)`, registers the input with `FastLED.add(config)`, applies MicInput gain with `Processor::setGain`, and polls FastLED's normalized bass/mid/treble levels, 16-bin equalizer (duplicated into Studio's established 32-slot spectrum), beat callback, and BPM getter. The generated sketch no longer compiles a second ESP32 I2S driver or self-contained FFT. `FFTAnalyzer` consumes the FastLED band globals and a live `BeatDetect` consumes FastLED's native beat/BPM; when no mic exists, generated audio outputs remain silent. `audioEngineForGraph(nodes)` lets a controller host one processor while pattern subgraphs use `{ externalAudio: true, nativeFastLedAudio: true }`. The microphone path remains ESP32-only and deploy validation blocks incompatible boards. The prior custom mic engine was hardware-validated on 2026-06-28; the FastLED replacement compiled successfully against the vendored FastLED 3.10.3 for ESP32-S3 on 2026-07-17, and was itself hardware-validated live on-device as part of the generative-show run on 2026-07-24 (GitHub issue #106).

### DMX / Art-Net input

Design note: `docs/development/design/dmx-artnet-input.md` (the authoritative v1 contract).

`src/state/dmx.ts` defines `DmxSnapshot` — one universe as a 512-byte `channels` array plus `valid`/`live`/`packetRate`/`lastPacketAt`/`source`. The `dmx` `dataType` carries that whole object down one wire; `DMXInput` (input category, label "DMX / Art-Net") is the source and `DMXChannel` (signal) is the only decoder, exposing `value` (0–1), `byte`, `active` (`byte >= activeThreshold`), and `changed`. The diagnostic fields are for the node body's readout and are deliberately **not** graph outputs. Channels are 1-based in the UI, 0-based in the buffer; `changed` never fires on the first frame a node sees (evaluator keeps `{ last, seen }`; firmware a `static bool _dmxSeen_<id>`).

`inputMode` picks the transport, and the three runtimes deliberately don't line up: **preview is Art-Net only, in both modes** — the helper (`/api/artnet/start|stop|status|snapshot` in `backend/app.py`) owns a long-lived UDP socket + per-universe cache, `dmxStore.ts` polls status/snapshot every 350 ms, and a `DMX512` node says so in its body rather than pretending. Firmware `Art-Net` emits a `WiFiUDP` listener (opcode `0x5000`, universe filter, 2000 ms staleness) on ESP32/ESP8266; firmware `DMX512` emits an `esp_dmx` receiver on the selected UART (1000 ms staleness), ESP32-only, and copies from `_dmxRaw + 1` to skip the start code. The `fbuild` engine vendors `esp_dmx` on the first DMX512 build (`_ensure_fbuild_esp_dmx_lib`); `arduino-cli` does not. Preview holds exactly **one** live universe (`dmxStore` is a singleton, last-mounted node wins) — multi-universe is out of v1, as are sACN, DMX transmit, and a helper-side DMX dongle.

**Wi-Fi credentials never enter the project.** `wifiSsid`/`wifiPassword` live in the browser-local `src/state/networkCredentials.ts`, keyed by node id; codegen and `validateGraph` look them up from there, and `graphStore` migrates + strips any previously-saved property values on load. Generated firmware still embeds the plaintext credential — unavoidable — so the export/upload trust warning covers it. The rest of the network config (`wifiHostname`, `useDhcp`, `staticIp`/`staticGateway`/`staticSubnet`/`staticDns`) stays on the node, gated by `isPropertyEnabled`. One sketch emits a single shared `_wifiEnsureConnected()` used by every Art-Net `DMXInput` **and** every NTP `RTCInput`; the first node's settings win, and `validateGraph` warns when they disagree rather than silently picking one. `previewPort` is a misleading name — the Art-Net firmware branch binds its socket to the same property; renaming it needs a saved-project migration.

Neither transport is hardware-validated. Both stay experimental in `docs/release/beta-support-matrix.md` until a DMX512 pass and an Art-Net pass are recorded.

### C++ Code Generator

`src/codegen/cppGenerator.ts` — `generateCpp(nodes, edges)` topologically sorts the graph and emits a FastLED `.ino` sketch. Each node type has a `case` in the `emit()` switch that writes to `loopLines[]`. The `needsT` flag enables a `float t = millis() / 1000.0f` variable only when needed. Inputs are resolved to C++ expressions via `floatExpr()`, `colorExpr()`, `boolExpr()`.

**Only what feeds an output is emitted.** `reachableFromOutputs` walks backward from every `MatrixOutput` before the topological sort, so a parked pattern or an abandoned branch contributes nothing. This matters because a dead frame/field node's cost is *not* something the compiler can remove: its `buf_`/`field_` buffer is a global, and the render code writing it ran every loop — after `FastLED.show()`, on pixels nothing displays. `Board` is a root alongside the outputs: it carries no ports and is read as configuration (`selectedPhysicalBoardProfile`), so it is never "unreachable". A graph with no output at all is left intact; `validateGraph` reports the missing output instead.

**The terminal node renders into `leds`.** When the output's blit is the plain unmapped `memmove` — a single non-HUB75 route, no ring map, no supersample, no XY table — and the node feeding it has no other consumer, that node's buffer is declared `CRGB* const buf_<id> = leds;` and the copy is dropped. Every reference in the loop is unchanged, so this is a declaration change, not a rename. It saves one full frame buffer plus a per-frame full-frame copy. It is deliberately **off for show pattern bodies** (`aliasTerminalBuffer: false` from `showGenerator`): a show runs every pattern through the same `leds`, so an aliased terminal would be clobbered by the other pattern mid-transition, and a persistent-buffer node (`Trails`, `FrameFeedback`, `ColorTrails`, `Code`) would lose its accumulated frame entirely. `estimateFirmwareRam` mirrors the same conditions.

### Upload UI (node-local)

Upload is driven **from the MatrixOutput node** — there is no separate modal (the old `UploadPanel` was removed). `src/components/Upload/MatrixOutputUpload.tsx` renders in the node body: a **⚙ Board** button (opens the board popup), a `<board> · <port>` label, an inline **Upload readiness** checklist (helper, active engine, board toolchain/core, port, and local upload access, each with `Ready` / `Checking` / `Fix` and one-click recovery actions like `Retry helper`, `Fix engine`, `Install core`, `Choose port`, or `Refresh ports`), an **Upload** button that shows inline status (`Compiling… / Uploading 42% / ✓ Done / ✗ Error`), a **🧪 Flash Wiring Test** action (a standalone diagnostic sketch for colour order, brightness/current-limit, orientation, panel numbering, and logical/physical pixel-chase checks using the current MatrixOutput settings, even with no frame wired), a conditional **🧭 Flash HUB75 Topology** action for a valid folded 2D HUB75 panel grid, a **↻ Re-upload last sketch** shortcut (cached per project; re-sends the most recently uploaded sketch without regenerating it), an **Export .ino** button, an **♪ Upload show to SD** button (only when an `SDCard` node is wired), and a small **⌗ Output** button. Three global overlays (rendered in `App.tsx`, driven by store flags): **`BoardPopup`** (a boards-manager list to toggle which boards appear in the dropdown + per-board core install/status, then board + port dropdowns and the resolved `<board> · <port>` label), **`ArduinoCliPopup`** (shown when the helper is up but `arduino-cli` is missing — *Locate…* a binary or *Install* one), and **`OutputConsole`** (a dismissible slide-over streaming the detailed compile/upload log).

`validateGraph()` (`src/utils/validateGraph.ts`, unit-tested) still checks for MatrixOutput, a connected frame port, and isolated nodes. Building/flashing is done **locally via `arduino-cli`** rather than a cloud compile service or in-browser WebSerial flashing.

**Live streaming to hardware.** An alternative to a compile+flash cycle on every tweak: `MatrixOutputUpload` adds an **⚡ Flash Stream Receiver** button (one-time flash of a tiny generic Adalight-protocol receiver, `src/codegen/streamReceiverGenerator.ts` — bakes in the MatrixOutput's width/height/chipset/colour-order/pins via the same `ledHardwareFromProps`/`fastledSetupCpp` helpers the normal sketch uses, then just waits for the classic `"Ada"` + hi/lo + checksum header and shows `NUM_LEDS` RGB triples with no `XY()` of its own) and a **📡 Live Stream** toggle that pushes the already-computed live-preview frames straight to the board over the same serial port instead of regenerating/recompiling. `src/state/streamStore.ts` holds the on/off + fps state; `publishStreamFrame(frame, w, h)` is called every tick from `LEDPreview.tsx`'s render loop (a plain module-level holder, not Zustand state, since it must not trigger a re-render 60×/sec) and a `setInterval` send-loop in the store reads the latest frame at a capped 30 fps, builds an Adalight packet (`src/utils/adalight.ts` — resolves serpentine wiring into physical strip order client-side, mirroring the C++ `XY()` formula, since the receiver has none of its own) and POSTs it to the helper. The helper (`backend/app.py`) holds the serial port open across many small `/api/stream/frame` POSTs between `/api/stream/start`/`/api/stream/stop` (reopening the port every frame would blow the frame budget) — the one place in `app.py` a serial port outlives a single request. `/api/upload` and `/api/upload-show` refuse to start while the same port is streaming (409), and `uploadStore.runUpload`/`runShowUpload` call `useStreamStore.getState().stop()` first so starting a normal upload always reclaims the port. `runUpload` takes an `opts.cache: false` flag so flashing the receiver sketch doesn't clobber the project's "re-upload last sketch" cache. **Hardware-validated** on an ESP32-S3 (16×16 WS2812B matrix, serpentine) via `fbuild` (2026-07-15): flashed the receiver, then Live Stream pushed frames over serial successfully. A later freeze investigation (2026-07-24) found the receiver's per-byte `while (!Serial.available()) {}` reads had no timeout — one byte lost to a UART RX overflow during `FastLED.show()`'s interrupts-disabled window permanently desynced it with no error visible to the host; every read is now bounded (`readByte()`/`READ_TIMEOUT_MS`) so a dropped byte costs one frame instead of the session. The deeper, more frequent freeze turned out to be unrelated to the receiver or the write path entirely: `vite-plugin-upload-helper.ts` spawned the helper with piped stdout/stderr that nothing ever read, so uvicorn's own access-log lines eventually filled the OS pipe buffer (~64KB on Windows) and the next stdout write blocked the whole process from the inside — fixed by piping both streams through to the parent. **Re-validated** (2026-07-24, `hw-f31a7f82`): 5+ minutes of sustained 30 fps live streaming with no freeze. **Bug found via a failed validation on ESP8266**: a NodeMCU (10×1 WS2812B strip, `arduino-cli`, 2026-07-25, `hw-b0b34ed3`) failed both LED output and the live-stream check, even though the exact same board/chipset/strip/engine combo passed Normal USB upload and Flash Wiring Test minutes earlier — narrowing it to the Adalight receiver/live-stream path specifically, not wiring or power. Root cause: `LEDPreview.tsx`'s render loop published `publishStreamFrame(frame, gW, gH)` using the *display* grid dimensions, which are floored to a minimum of 2 for canvas/WebGL sizing — a 1-row strip (`height: 1`) produced a real 1-row frame but published `height: 2`, permanently disagreeing with the receiver's correctly unclamped baked `HEIGHT`. `streamStore.ts`'s send loop silently drops every frame on a width/height mismatch, so streaming never started at all: fps stuck at 0, no error. Not ESP8266-specific — any 1-row/1-col strip layout on any board hit this. Fixed by publishing the frame array's own actual shape instead of the clamped display dimensions. **Re-validated** (2026-07-25, same `hw-b0b34ed3` configuration key): all checks passed, including live-stream frames actually reaching the board.

**Standalone wiring diagnostics.** `src/codegen/wiringDiagnosticGenerator.ts` generates a self-contained sketch from the current `MatrixOutput` settings for board bring-up before a full graph exists. Addressable outputs reuse the same `ledHardwareFromProps` / `fastledSetupCpp` path as normal uploads, honour the baked `XY()` remap and optional FastLED power cap, and cycle through RGB colour-order solids, a brightness/current-limit bar pattern, an orientation gradient with corner markers, per-panel numbering with a top-left notch, a logical XY chase, and a direct physical-index chase. A valid folded HUB75 Panels layout adds a ninth, topology-specific phase and exposes **🧭 Flash HUB75 Topology** as a dedicated held mode: every physical tile gets fixed-colour corner marks, red +X/blue +Y axes, its `(x,y)` grid coordinate, configured rotation, chain ordinal, and a yellow direction arrow that reverses on serpentine rows. This pattern is driven from the same `tilesX`/`tilesY`/`tileSerpentine`/`tileRotations` properties as normal HUB75 codegen; its logical CRGB buffer stays row-major so `VirtualMatrixPanel_T` and the HUB75 coordinate map remain the single owners of fold/rotation routing. `findHub75TopologyDiagnosticErrors()` gates the dedicated action without treating a valid single-panel/one-row configuration as an unhealthy graph. Both wiring actions flash with `runUpload(..., { cache: false })` so they don't replace the project's cached normal sketch. **Hardware-validated** on an ESP32-S3 (16×16 WS2812B matrix, serpentine) via `fbuild` (2026-07-15): flashed and confirmed LEDs displayed correctly. **Re-validated** (2026-07-24, `hw-59a1bb36`): full diagnostic sequence (solids, gradients, corner marks, indices, chases) confirmed correct. **Also hardware-validated** on an ESP8266 (NodeMCU, 10×1 WS2812B strip) via `arduino-cli` (2026-07-25, `hw-7adaec6f`): full diagnostic sequence confirmed correct. The HUB75 2D topology mode is implemented and generator/validation-tested but not yet hardware-validated.

### Upload Helper (`backend/`)

A browser page can't launch a local CLI, so `backend/` is a small **FastAPI** service the app POSTs to. **It is auto-launched** by `vite-plugin-upload-helper.ts` (wired into `vite.config.ts`): the dev/preview server TCP-probes `:8008` and, if nothing's there, spawns `python -m uvicorn app:app --port 8008 --app-dir backend`, killing the child on server close. (`npm run helper` still starts it manually; if Python/deps are missing the app runs fine, upload just stays dark.) Endpoints: `/api/health` (liveness + whether `arduino-cli` is found), `/api/serial/ports` (`board list`), `/api/upload` (compile then `upload -p PORT`, streaming logs), `/api/compile-check` (compile-only capacity check, one JSON result — see *Live controller-capacity meter* below), `/api/upload-show` (music-sync flow, below), `/api/cores` + `/api/core/install` (board-manager core list/install, registering third-party board URLs first), and `/api/arduino-cli/locate` + `/api/arduino-cli/install` (point the helper at a user-supplied binary, or download the official one into `backend/bin`). The resolved CLI path is **persisted** to `backend/.helper-config.json` (gitignored), so `_find_arduino_cli` checks: saved path → `ARDUINO_CLI` env → `PATH` → Arduino IDE bundle → self-installed `backend/bin`. `src/utils/backendClient.ts` is the frontend client (`checkBackend`/`listPorts`/`listCores`/`uploadSketch`/`uploadShow`/`compileCheck`/`locateCli`/`installCli`/`installCore`); `BACKEND_URL` defaults to `http://localhost:8008` (override via `VITE_BACKEND_URL`).

**Build engine.** Two engines compile/flash the generated sketch, chosen by `_active_engine()` (fbuild preferred, arduino-cli fallback) and reported at `/api/health`/`/api/engine` (`GET`/`POST`). **`fbuild`** (FastLED's own PlatformIO-compatible tool, `pip install fbuild`) manages its own per-board toolchains — no arduino-cli-style core install — via a persistent scaffold at `backend/.fbuild-project/` (`_ensure_fbuild_project`/`_write_fbuild_ini`, one `[env:X]` per `BOARDS` entry from `uploadStore.ts` + PSRAM variants) that `_compile_upload_fbuild` builds/deploys against, translating fbuild's own output into the same `=== label ===`/exit-code markers `parseStatus()` expects. One remaining fbuild-specific workaround, load-bearing: FastLED and (for the music-sync Player) `ESP32-audioI2S` are **vendored** via `git clone` into `.fbuild-project/lib/` (`_ensure_fbuild_audio_lib`) rather than declared in `platformio.ini`'s `lib_deps` — fbuild 2.4.0's registry dependency resolution doesn't actually fetch anything (`fbuild sync` marks entries `unresolved`). A second workaround — writing the generated source as `main.cpp` instead of `main.ino` (`_write_fbuild_main`), because fbuild's `.ino`→`.cpp` preprocessing used to auto-insert function prototypes *before* any user `#include`s and broke FastLED-typed helpers like `CRGB kelvinToRGB(...)` — was **removed 2026-08-10** now that fbuild 2.5.16 fixes the root cause upstream (FastLED/fbuild#1275: sketch `#include`s are hoisted into the prelude ahead of the generated prototypes); `requirements.txt`/`constraints.txt` pin `fbuild>=2.5.16` and `_write_fbuild_main` writes plain `.ino` again. **Hardware-validated** since the revert on a classic ESP32 (Generic 38-pin DevKit, 16×16 WS2812B, `fbuild` 2.5.16, 2026-08-16): the generated `.ino` compiled, flashed, and ran. Note the pin is a floor, not a guarantee the environment honours it — that validation run first hit a helper still carrying fbuild 2.5.15, which would have reintroduced the exact prototype breakage the revert assumes is fixed. Windows also needs long-path support enabled (`LongPathsEnabled=1` in the registry) or ESP32 builds fail intermittently on a different vendored-toolchain file each run once the path depth crosses `MAX_PATH`. **Hardware-validated** on a real ESP32-S3 (16×16 WS2812B matrix, serpentine): fbuild compiled a live-graph-generated sketch, flashed it via `esptool`, and the uploaded pattern ran correctly. **`arduino-cli`** (fallback) is the original engine — see below for its own endpoints.

**Music-sync upload (SD card).** When an `SDCard` part is on the bench (hardware view only on the `Hardware` branch — it carries no signal, so it has no ports and no canvas presence), the Upload tab offers "Upload show to SD". `src/utils/showUpload.ts` (`sdCardConnected`/`buildShowPayload`) assembles a **provisioner** sketch (`provisionerSketchGenerator.ts`), the **player** sketch (`playerConfigFromGraph()` pulls LED config from MatrixOutput + SD/I2S pins from SDCard), and the SD file list (`/music/<title>.mp3` from `entry.file`, `/shows/<title>.show` from `showFileToBinary`). `/api/upload-show` (multipart) then: ① compiles+uploads the provisioner, ② opens the serial port with pyserial and runs the provisioner wire-protocol (`PING`→`READY`, then `PUT <path> <n>` + `PROVISION_CHUNK`-byte blocks with a per-block `A` ack, `DONE`/`END`/`BYE`) to write each file to the card, ③ compiles+uploads the player. The protocol's two sides are `provisionerSketchGenerator.ts` (device) and `_serial_send` in `backend/app.py` (host) — keep them in sync.

### Music-Sync Show Pipeline

A second, **offline** authoring path (distinct from the live preview/codegen flow above) turns audio tracks into timed LED "shows" the ESP32-S3 plays back in sync. It is a three-node chain spanning the `audio` and `hardware` categories, wired by new `dataType`s `songs` and `shows`:

`MusicLibrary` (drop MP3s) **→** `PerformanceGenerator` (rules engine) **→** `SDCard` (export ZIP).

- **`src/audio/musicAnalyzer.ts`** — Web Audio API *offline* analysis of an uploaded MP3: BPM detection, per-~100 ms energy envelope (bass/mids/treble/overall), beat timestamps, section detection (intro/verse/buildup/drop/…), and mood (energy/valence/key) estimation. Returns the `SongAnalysis` shape in `src/types/showFile.ts`.
- **`src/codegen/performanceGenerator.ts`** — a rules engine that maps a `SongAnalysis` to a timed `ShowFile`: a sorted event stream of `SET_PATTERN`/`SET_PALETTE`/`SET_SPEED`/`SET_BRIGHTNESS`/`BEAT_FLASH`/`TRANSITION` commands. Tuned by the node's `beatIntensity`/`energySensitivity`/`transitionDuration`/`patternHold`/`paletteMode` properties. **Beat-aligned within-section cycling:** `patternHold` is a **minimum** hold (default 10 s), not a fixed slot length. `sectionSwitchTimes` holds each pattern at least `patternHold` seconds, then snaps the switch forward to the **next beat** (`nextBeatAtOrAfter`, falling back to plain time when the track has no later beat) so a change lands on the music. `detectEnergySurges` adds an extra beat-aligned switch on a significant mid-section energy rise (a sub-drop), gated to stay ≥ half the minimum hold from its neighbours; higher `energySensitivity` lowers the surge threshold. Section boundaries always switch (drops/choruses are their own sections). Collapses to a single pattern when fewer than two patterns are eligible for the section, or when the section is too short to fit another beat-aligned hold. Applies to both enum and collection modes; `SET_PALETTE`/`SET_SPEED`/`SET_ENERGY` stay section-level. The `TRANSITION` and its incoming `SET_PATTERN` now share the same instant `st` (transition ordered first) so the transition runs over `[st, st+transitionDuration]` from that point — mirrored by both the preview (`showPreview.renderShowFrame` composites the outgoing/incoming frames via `compositeTransition`) and the firmware player (`playerSketchGenerator` renders the outgoing pattern into `showA`, the incoming into `showB`, and composites A→B into `leds` by progress). All **16 transition styles** run on-device: the player emits a self-contained `compositeTransition(type, out, a, b, tt)` C++ helper ported from graphEvaluator's, using the same default direction/axis/tile/count/turns the preview falls back to (a `.show` transition carries only its style id + duration). **Beat accents** are not just white flashes: each eligible beat is either a `BEAT_FLASH` or a `PARTICLE_BURST` (favoured in high-energy sections) — a burst of short-lived colored sparks (`intensity`+`hue`+`style` params) whose `style` indexes **`PARTICLE_STYLES`** in `performanceGenerator.ts` — currently **17 motions** (`rise`/`rain`/`explode`/`fireworks`/`swirl`/`twinkle`/`ring`/`fountain`/`helix`/`meteor`/`confetti`/`sparkle`/`comet`/`snow`/`gravity`/`bubbles`/`vortex`); the list is append-only, since a `.show` file stores the raw index. The spawn+motion is a pure function of burst-time + spark index (a shared `prnd` GLSL-style hash), so the preview (`particleOverlayAt` in `showPreview.ts`) and firmware (the `switch (burstStyle)` particle block in `playerSketchGenerator.ts`, `PARTICLE_LIFE_MS`/`PARTICLE_COUNT`) spawn the same sparks — the two `switch (style)` blocks must stay in sync with each other *and* with `PARTICLE_STYLES`' ordering (case 0 is the `default:` arm in both); both host a single active burst. **Fade to black on silence:** `detectSilences` finds spans where overall energy stays below a threshold, and the generator emits stepped `SET_BRIGHTNESS` ramps to 0 and back to the section level (`sectionBrightness`), so a quiet gap goes dark and the sparks/flash fade with it.
- **`src/types/showFile.ts`** — the `.show` format: a compact, sorted event stream (timestamps in ms from song start) the player binary-searches by audio position for frame-perfect A/V sync, plus an optional trailing **baked audio envelope** (`ShowFile.audio`: a fixed-rate `bass`/`mids`/`treble` track). Also defines the `SongAnalysis`/`BeatInfo`/`EnergyPoint`/`SongSection` analysis types.

- **Baked audio envelope (song-synced FFT).** So a collection pattern's `FFTAnalyzer` reacts to the *song* on-device (deterministic, no live mic), `generateShow` bakes the analysis's ~100 ms energy track up to a fixed 50 Hz `bass`/`mids`/`treble` envelope via `bakeEnvelope` (`ENVELOPE_RATE_HZ`) and `showFileToBinary` appends it after the events (`rate(1) + frameCount(4) + 3 bytes/frame`, quantised 0–255; old players ignore the trailing bytes). When the show carries an envelope, `buildShowPayload`/`exportShowPackage` compile the patterns with `externalAudio` and pass `{ audioEnvelope: true }` to `generatePlayerSketch`, which hosts the `_audioBass`/`_audioMids`/`_audioTreble` globals + a coarse `_audioSpectrum[32]` (bass→low bins, mids→mid, treble→high, so BeatDetect/PercussionDetect still respond), loads the envelope in `loadShowFile`, and interpolates it per frame in `updateShowAudio(posMs)`. Only baked when the analysis has an energy track and only hosted for collection (version-2) shows. First slice: 3-band envelope feeding FFTAnalyzer; a full baked spectrum and preview parity (the browser preview still reads the live mic for these nodes) are follow-ups. Not yet hardware-validated.
- **`src/codegen/playerSketchGenerator.ts`** — emits a FastLED + **ESP32-audioI2S** player `.ino` that slaves LED commands to `audio.getPosition()`. The `SDCard` node properties configure its pins (SD CS, LED data, I2S BCLK/LRC/DOUT), matrix size, chipset/colour order, and volume.
- **`src/utils/zipExport.ts`** — a zero-dependency ZIP builder; `SDCard` packages the `.show` files + the generated player sketch into one downloadable archive (drop onto the board's SD card).
- **`src/state/musicStore.ts`** — Zustand store managing the analysis queue and generated shows; **`src/components/Canvas/MusicLibraryNodeBody.tsx`** is the library UI (engine toggle, drop zone, per-song status, *Analyse All* / *Export ZIP* / *Clear*) rendered **directly in the `MusicLibrary` node body** in `StudioNode` (the node widens to fit; interactive controls carry `nodrag`, the song list `nowheel`). `MusicLibrary` is an **audio**-category node (the song source), not a menu-bar button — there is no separate modal panel.
- **`src/state/showPreview.ts` + `src/components/Canvas/PerformanceGeneratorBody.tsx`** — the in-browser show preview rendered in the `PerformanceGenerator` node body: `showStateAt`/`beatFlashAt`/`renderShowFrame` mirror the on-device player (each `SET_PATTERN` evaluated through a synthetic one-node graph), driving a `<canvas>` + transport off the song's audio clock so a generated show can be watched in sync before export. Generator-option changes regenerate the affected songs after a short debounce. `PerformanceGenerator` has no `frame` graph port — a firmware-facing one could only ever render black, since a normal (non-SD-show) sketch has no audio transport to drive it. Instead, a **"Show in main LED preview"** checkbox in the node body sets the `showInMainPreview` node property; when on, the play/seek effects publish the playing show + position to `src/state/showPlayback.ts` (`setPlayback`/`clearPlayback`) instead of drawing the node's own small canvas, and `src/components/Preview/showPlaybackSignal.ts`'s `applyShowPlaybackSignal` (called from `LEDPreview.tsx`'s render loop) renders that show over the graph's own terminal frame — a preview-only feature, decoupled from graph wiring entirely.
- **Show editor / timeline** — **`src/components/Canvas/ShowTimeline.tsx`** (toggled via *✎ Edit timeline* in `PerformanceGeneratorBody`) is the hand-tweak editor: a scrubbable marker track (one dot per event, coloured per command, click-to-seek) over the song duration plus an editable, scrollable event list. Selecting an event opens command-appropriate controls (retime; change command; pattern/palette/style dropdowns sourced from `SHOW_PATTERNS`/`SHOW_PALETTES`/`SHOW_TRANSITIONS` so picks stay round-trippable through `showFileToBinary` — for a **collection (version-2) show** the `SET_PATTERN` dropdown instead lists the collection's patterns by group name and edits by **index**, resolving ids from the graph store; speed/brightness/intensity/decay/duration sliders) with **add / duplicate / delete**. Every mutation re-sorts via the shared `sortShowEvents` (the same time-then-command tie-break the generator uses) and persists through `musicStore.updateShow`, which sets `MusicEntry.edited` so the option-change auto-regen **skips** edited songs (manual edits win until **Revert** → `musicStore.revertShow` regenerates from the analysis and clears the flag). The preview canvas reflects edits live because it reads the same `show.events`.

These nodes have no `frame`/`palette`/`color` output, so they don't participate in the live LED preview or the `cppGenerator.ts` sketch — they are a parallel export pipeline. (Added in PR #58; show preview and timeline editor followed.)

**Collection-driven shows (slice 1 of `docs/development/design/collection-driven-performance.md`).** Wiring a `PatternCollection`'s `patternset` into the `PerformanceGenerator`'s new `patternset` input makes the rules engine schedule the user's *own* patterns instead of the 11 built-in names: `musicStore` resolves the wired collection's `patternIds` live from the graph and passes them to `generateShow(analysis, options, patternIds)`, which picks a random collection **index** per section and emits a **version-2** `ShowFile` (`SET_PATTERN.params.index` + a `patternSet` group-id array; `showFileToBinary` encodes the index). `showPreview.renderShowFrame` renders a v2 show by evaluating the indexed group's subgraph through the live group registry. For export, `buildPatternRenderers` (extracted from `showGenerator.ts`) compiles each collected subgraph into a `render_pN()` function, and `generatePlayerSketch(cfg, renderers)` swaps its built-in pattern switch for an index→`render_pN` dispatch — same audio sync / `.show` loader / beat-flash. Slice 1 renders patterns *as authored* (`SET_PALETTE`/`SET_SPEED` emitted but unused); the "Use group inputs" modulation is a later slice.

**Section-aware selection (slice 3).** Each collection pattern can be restricted to the song-section types it plays in. `PatternCollectionBody` renders a row of section chips (intro/verse/buildup/drop/chorus/bridge/outro) per absorbed pattern; toggling one calls `graphStore.togglePatternSection`, stored as `PatternCollection.properties.patternSections: Record<groupId, sectionType[]>` (an empty/missing entry = eligible in *any* section, pruned on the last untoggle). `musicStore.wiredCollection()` resolves `{ ids, sectionTags }` (tags aligned by index) live from the wired collection and threads them into `generateShow(analysis, options, patternIds, sectionTags)`, whose `chooseCollectionIndex(sectionType)` picks only among eligible patterns (untagged, or tagged with that section), falling back to the whole set when none match so a section always renders. `SECTION_TYPES` is exported from `performanceGenerator.ts` and shared with the chip UI. Untagged collections behave exactly like slice 1's random pick.

**Group-input modulation (slice 2 — `energy`/`speed`/`palette` roles).** The `PerformanceGenerator.useGroupInputs` toggle drives each collected pattern's exposed `GroupInput` "roles" from the analysis. A pattern opts in by exposing a `GroupInput` whose `paramId` is a role name — `energy`, `speed`, or `palette`, picked from the **role dropdown** on the GroupInput node body (`StudioNode` renders it specially in place of the raw `paramId` field; "— input —" = an untagged input, `paramId` `param0`). The dropdown calls `graphStore.setGroupInputRole`, which sets both `paramId` and the output port `dataType` (`palette` for the palette role, else `float`). Since `GroupInput` nodes are otherwise only auto-minted from incoming boundary edges at group-creation time, a **＋ Input** button in `GroupControls` (shown only inside a group) adds one via `graphStore.addGroupInput` — so you enter a self-contained pattern group (double-click it), add an input, pick its role, and wire its output to the knob it should drive. The generator emits a `SET_ENERGY` event (0–1 section energy) per section; the **`speed` role reuses the existing `SET_SPEED`** event (no new command), normalising its 0–2 multiplier to 0–1 (`min(1, speed/2)` in preview; `constrain(params[0]*0.5f, 0, 1)` in firmware, which still also sets the global `animSpeed`); the **`palette` role reuses `SET_PALETTE`** (preview feeds the studio palette name via `PALETTE_MAP`; firmware adds a `CRGBPalette16 palette` global + a `paletteFromId()` helper mirroring `samplePalette`'s preset switch, updated by `CMD_SET_PALETTE`). **Preview:** `renderShowFrame(show, ms, W, H, groups, useGroupInputs)` evaluates the pattern group's subgraph directly (its `GroupOutput` terminal) and, when on, passes `{ energy, speed, palette }` through the evaluator's `groupInputs` path. **Codegen:** with `useGroupInputs`, `buildPattern` keeps role-tagged `GroupInput` nodes (instead of stripping them) and `generateCpp` emits them as `float n_<id>_out = <paramId>;` (float roles) or `CRGBPalette16 pal_<id> = palette;` (palette role, referenced via `paletteExpr`); `buildPatternRenderers(ids, groups, roleParams)` widens each `render_pN` to `(uint32_t ms, float energy, float speed, const CRGBPalette16& palette)` — type per role via `ROLE_CPP_TYPE` — and reports `params`; `generatePlayerSketch` declares the role globals, handles their commands, and threads them into the dispatch (`buildShowPayload` passes `['energy','speed','palette']` when the toggle is on). How the role value *combines* (replace vs. scale) is authored inside the pattern (e.g. wire the role through a `Math` multiply; palette is opt-in per input so a two-palette blend doesn't collapse). Off by default; only hardware validation remains for slice 2.

### Bundled nodes

Several former node types are collapsed into one **bundled** node, selected by a variant property (the pattern to follow when consolidating other identical-signature clusters):

- **`Noise`** — `noiseType` (`field`/`simplex`/`noise3d`/`noise4d`/`worley`/`plasma`/`sine`); folds the former NoiseField/Simplex2D/Noise3D/Worley/PlasmaFractal/Noise2D. Every variant writes a raw scalar `field` and maps it through a palette for the `frame` output (the old Noise2D's self-coloured HSV output is gone — `sine` is now palette-driven like the rest).
- **`Math`** — `mathOp` (`add`/`subtract`/`multiply`/`divide`/`min`/`max`); folds MathAdd/Multiply/MinNode/MaxNode (`subtract`/`divide` are new ops). Mod (`x,m` ports) and Compare (bool out) stay separate.
- **`Transition`** — `transitionType` selects one of **16** A→B effects: `crossfade`/`wipe`/`dissolve` plus `iris`/`clockwipe`/`push`/`checkerboard`/`diagonal`/`fadeblack`/`fadewhite`/`blinds`/`ripple`/`spiral`/`curtain`/`scanlines`/`zoom`. Variant-specific props (`direction` for wipe/push, `axis` for blinds/curtain, `tileSize` for checkerboard, `count` for blinds, `turns` for spiral) are gated by `isPropertyEnabled`. The C++ generator emits real buffer compositing per variant (seed `ob` from A, write B in), not just the three originals.
- **`Blend`** — `blendMode` (`normal`/`multiply`/`screen`/`overlay`/`add`/`difference`); replaces LayerBlend + BlendFrames. Composites B over A per mode, mixed by `amount` (opacity, **0–1**; scaled ×255 in the evaluator + codegen for FastLED's `nblend`). `Blur2D`/`PaletteBlend` share the same 0–1 `amount`. Migration rescales any legacy 0–255 `amount` (value > 1 ⇒ old scale) to 0–1 on load. The `normal` path emits FastLED `nblend`; other modes emit a per-channel blend loop in C++. (The former BlendFrames used a 0–1 `t` port, so its migration carries `t`→`amount` and rewires that edge — the one bundle whose port id changed.)
- **`FieldMath`** — `fieldOp` (`add`/`subtract`/`multiply`/`mix`/`min`/`max`/`difference`); combines two `field` inputs into one. `mix` blends by a scalar `t` input; the rest are per-pixel operations. Dispatches on `fieldOp` in the evaluator and codegen.
- **`Particles`** — `particleType` selects one of **20** movement styles (`fountain`/`gravity`/`fireworks`/`sparkle`/`comet`/`snow`/`swarm`/`rain`/`embers`/`bubbles`/`vortex`/`orbit`/`confetti`/`fireflies`/`meteor`/`tornado`/`pinwheel`/`bounce`/`attractor`/`waterfall`) on a single stateful particle-system node. Beyond the shared `rate`/`decay`/`paletteIn`, five extra controls are gated to the modes that actually use them via `isPropertyEnabled` (shown-but-disabled elsewhere, the same convention as `Transition` below): `size` scales the rendered particle radius (every mode); `count` sets the pool size directly for the fixed-population modes (`swarm`/`orbit`/`bounce`/`fireflies`), decoupled from spawn `rate`; `spread` widens/narrows the spawn area for width-spawning modes (`fountain`/`gravity`/`sparkle`/`rain`/`confetti`/`snow`/`waterfall`); `gravity`/`bounce` scale a mode's built-in accel/restitution constant (`fountain`/`gravity`/`fireworks`/`waterfall`, and `gravity`/`waterfall` respectively). These five are plain properties (not wired ports, unlike `rate`/`decay`) — mirroring `Transition`'s per-variant props — and the evaluator/codegen apply them directly inside each mode's own spawn/update formula, so preview and firmware stay in lockstep.
- **`Ease`** — `easeType` offers linear, legacy in/out (`inOutCubic`, `inOutQuad`, `inOutApprox`), directional quad/cubic/sine, and triangle/quad/cubic wave variants. It maps a 0–1 value through the matching FastLED 8-bit primitive and normalizes the result back to 0–1. The evaluator's shared `applyEase` mirrors the generated `ease8*`, `fl::ease*8`, and `*wave8` calls; the five original ids retain their established preview and firmware behavior for saved projects.
- **`Trigger`** — `triggerOp` (`debounce`/`toggle`/`oneShot`/`pulseDivider`/`delay`); a single bool-in/bool-out edge-utility node. `debounce` commits a change only once the input has held stable for `stableTime`; `toggle` flips on each rising edge; `oneShot` holds true for `holdTime` after a rising edge (ignoring retriggers while already high); `pulseDivider` fires only every `divideBy`th rising edge; `delay` fires once, `delayTime` after the edge. The evaluator keeps one combined state bag per instance (`triggerState`); codegen mirrors each variant with millis()-based statics so preview and firmware timing match.

Mechanics: each variant set lives in `PROPERTY_META` (the inline dropdown); the evaluator and C++ generator dispatch on the variant property in their single `case`; `graphStore.loadGraph` (via `migrateLegacyGraph`/`LEGACY_BUNDLE`) migrates the legacy node types — and any renamed edge handles — on import. `nodeDisplayLabel()` makes the node header reflect the selected variant, and `isPropertyEnabled()` disables an inline editor that doesn't apply to the current variant (e.g. Transition `direction`) while still showing its value. Bundling is **by identical port signature** — properties may differ between variants (Blend is the one exception, unifying two near-identical nodes whose mix-port id/scale differed).

Some node types are created programmatically rather than dragged from the sidebar (so they have no `NODE_LIBRARY` entry): `Group` and `GroupOutput`/`GroupInput` are minted by `graphStore.createGroup` (see the multi-graph/group section above).

The `Text` node renders with the built-in 3×5 bitmap font in `src/state/font.ts`. The font is plain data (`FONT`, `BitmapFont`, `textColumns`, `textLines`, `textBlockLayout`, `asFont`) shared by the evaluator and the C++ generator so preview and firmware match exactly. Multi-line text is newline-aware in both paths: each logical line gets its own bitmap column run, the full text block carries a shared width/height, and rows stack with a fixed 1-pixel gap so alignment, wrap, and horizontal/vertical scroll behave identically in preview and generated firmware. A Text node can carry a **custom font** in `properties.font` (a `{ w, h, glyphs }` object, uploaded as JSON via the Inspector); `asFont()` validates it and everything else (rendering, scrolling, codegen) reads the resolved font's dimensions, so no other code changes are needed. The Inspector treats `text` as a multiline textarea and shows a dedicated font manager card (source, dimensions, glyph count, replace/reset actions, JSON shape hint) instead of the old inline upload link.

The `Poline` node generates a smooth palette via the **poline** library (polar interpolation between two anchor colours). `src/state/polinePalette.ts` wraps it (`polinePalette` → `RGB[]` for the evaluator/preview, `polineStops16` → 16 stops the C++ generator bakes into a `CRGBPalette16`, plus the position-function list mirrored in `PROPERTY_META.position`). Anchors come from two wired `color` inputs; the per-anchor `anchorA`/`anchorB` hex props are the fallback when unwired and the values codegen bakes (live-wired anchors drive only the preview). Like `CustomPalette`/`PaletteBlend`, a connected `Poline` resolves to `pal_<id>` in `paletteExpr`.

The `Image` node follows the same shared-data pattern via `src/state/image.ts`: an uploaded picture is downscaled to ≤`IMAGE_MAX_DIM` (32) and stored in `properties.image` as `{ w, h, pixels }` (flat `r,g,b` bytes). `asImage()` validates it; `sampleImageToFrame()` nearest-neighbour samples it to the matrix for preview, and the C++ generator emits the same pixels as a `PROGMEM` array blitted with `pgm_read_byte`. Its original `frame` output remains first and unchanged; a second `image` output exposes the validated raw upload for data-only consumers. Upload is handled inline by `ImageNodeBody` (`src/components/Canvas/ImageNodeBody.tsx`): a drop zone (drag-and-drop or click to browse) when no image is loaded, or a pixelated thumbnail + dimensions + clear button when one is. Like `font`, the `image` object is excluded from the generic Inspector field list.

**Palette from Image.** `PaletteFromImage` (color / Palettes) consumes that raw `image` port and extracts 2–8 representative anchors in `src/state/imagePalette.ts` using a five-bit RGB histogram plus weighted median-cut quantisation. Pixel alpha and animated-frame duration contribute to the histogram weight; fully transparent pixels are ignored. Anchors are ordered dark→light and expanded through `customPaletteStops16` into the standard 16-entry palette value. The preview caches extraction by uploaded-object identity and anchor count. Codegen calls the same helper once while generating the sketch and bakes the stops into `CRGBPalette16 pal_<id>`, so firmware has no runtime extraction or histogram RAM cost. A missing/unwired image deliberately yields black.

**Float-field pipeline (ANIMartRIX — Phase 1 of `docs/development/design/animartrix-float-field.md`).** A new `field` port `dataType` carries a per-pixel scalar grid (`Float32Array`, length W×H, values 0–1) — the `Field` type in `graphEvaluator.ts`, added to `PortValue`. `FieldFormula` evaluates a per-pixel expression into a field; `FieldToFrame` maps a field through a palette into a `frame` (the only `field`→`frame` conversion). Both, plus the existing `CustomFormula`, expose centred/polar vars (`cx`, `cy`, `r`, `angle`) and FastLED fixed-point shims (`sin8`/`cos8`/`sin16`/`beatsin8`/`beatsin16`/`scale8`/`qadd8`/`qsub8`) so ANIMartRIX-style one-liners work verbatim — `FieldFormula` uses integer `x,y`, `CustomFormula` keeps `x,y` normalised 0–1 for backward compatibility. The shims live in **`src/state/fastledShims.ts`**, shared by the evaluator (`makeShims(t)` supplies callable values to `formulaLang.ts`'s closed parser/interpreter, cached in `fieldFormulaCache`/`formulaCache`) and the codegen (`CPP_SHIM_HELPERS` emits float wrappers like `_fsin8`, `cppRewriteShims` rewrites call sites so `sin8(x)/255` stays float division on-device). Field-producing nodes get a `float field_<id>[NUM_LEDS]` buffer in the generated sketch, parallel to the `CRGB buf_<id>` frame buffers. **Phase 2** adds field-composition nodes: `DistanceField` (distance from each pixel to a movable point, `scale` stretches the ramp), `FieldMath` (combine two fields — `fieldOp` of add/subtract/multiply/mix/min/max/difference, a bundled-title node), and `FieldWarp` (sample a field at coordinates pushed by `dx`/`dy` offset fields, nearest-neighbour and edge-clamped) — each `field`→`field`, composing freely before a terminal `FieldToFrame`. **Phase 3** adds coordinate-space transforms `FieldRotate` (rotate a field around its centre by an `angle` input + `spin` deg/sec, edge-wrapping) and `FieldTile` (repeat a field `tilesX`×`tilesY`); these are whole-field coordinate remaps (distinct from `FieldWarp`'s per-pixel offsets), so they ship as standalone composite nodes.

**FastLED helper nodes.** A handful of nodes wrap a single FastLED primitive so preview and firmware match by construction (evaluator + codegen dispatch, no shims):

- **`HeatColor`** (color) — `heat` (0–1) → the black-body fire ramp. The evaluator reuses the shared `heatColor()` helper (also backing Fire2012), scaling 0–1 → 0–255; codegen emits `HeatColor()`. Pair with `FieldToFrame`'s `heat` palette for a field-driven version.
- **`Rainbow`** (pattern) — FastLED `fill_rainbow`: a scrolling hue sweep, `deltaHue` sets the per-LED spread. `speed` is a normalised 0–1 slider (`SPEED_MAX.Rainbow = 120` hue-units/sec in `speedRange.ts`); index order matches the `[y*W+x]` buffer layout so preview lines up with the sketch.
- **`Gamma`** (composite) — perceptual gamma correction, `frame`→`frame`. Evaluator applies `255·(c/255)^γ` per channel; codegen emits `napplyGamma_video(buf, NUM_LEDS, γ)`.
- **`Interval`** (signal) — a metronome that emits a `bool` pulse every `interval` seconds (the non-audio analogue of `EVERY_N_MILLISECONDS`). Stateful in the evaluator (module-level `intervalLast`, keyed per group instance like the other stateful nodes); codegen emits a `static uint32_t` millis timer.

**Signal utility nodes.** Small float/trigger plumbing that makes signals composable: `Smooth` (low-pass EMA toward the input with a `response` time constant — the tool for taming jittery FFT bands or a PotInput, since the cycle guard forbids self-feeding a `Lerp`), `SampleHold` (latches `value` on each rising edge of `trigger` — `Random → SampleHold ← BeatDetect` is the "new random value every beat" idiom; `Random` alone re-rolls every frame), `Envelope` (rising trigger edge → 1, linear decay to 0 over `decay` seconds — the generic float analogue of BeatFlash; wire through `Ease` for a curve), `Switch` (A/B float selector by a `sel` bool — unlike `Gate`, both branches are live signals), and `FrameSwitch` (the frame-typed A/B counterpart, composite category; falls back to the wired side when the selected one is empty, and evaluates both inputs so hidden stateful patterns keep advancing). The stateful three keep per-instance state in module-level maps (`smoothState`/`holdState`/`envState`, pruned like the rest) and their firmware mirrors use `millis()`-based statics seeded from the first sample, so preview matches on-device; all are dwell-time based, not framerate based.

**Trails (feedback buffer).** `Trails` (composite) is the canonical FastLED `fadeToBlackBy()`-and-accumulate idiom as a general-purpose node: it holds a persistent per-instance frame buffer (`trailState`, keyed like the other stateful nodes) that fades by `decay` each tick and is re-lightened per-channel wherever the incoming frame is brighter (`max(faded, input)`), so a moving highlight (a `Circle` driven by `Sin`/`Cos`, a `Blobs` charge, scrolling `Text`) leaves a comet trail instead of needing a pattern with trails baked in. Codegen mirrors the `Code` node's persistence trick: the node's own `buf_` render buffer is deliberately *not* reseeded from the input each frame (no `seedFrom`/`memmove`) — it fades and re-lightens in place via `fadeToBlackBy()` plus a per-channel `max`, exactly like the evaluator. Left untouched (not reset) while unwired so it resumes cleanly if reconnected; a graph with nothing ever wired in just renders solid black.

**Formula Points.** `FormulaPoints` (pattern / Simulations) is a curated stateful point/trajectory generator beside `Particles`: a `formulaType` dropdown of five variants instead of a particle system — `phyllotaxis` (golden-angle spiral scatter of `count` points, stateless — recomputed fresh each frame), `lissajousPath`/`rosePath` (a single comet tracing a Lissajous curve or a rose curve, each owning a persistent trail buffer), `logisticMap` (a chaotic scalar sequence — `x' = chaos·x·(1−x)` — plotted as `count` points around a ring each frame, its running `x` persisted across frames so the churn never resets), and `attractor` (a de Jong iterated map — unconditionally bounded to `[-2,2]` regardless of coefficients, so no escape/clamp logic is needed — with three named coefficient presets, `classic`/`swirl`/`web`, rather than exposing raw a/b/c/d sliders, the same convention `Fire`/`Fire2012` use for their `seed` LCG). `lissajousPath`/`rosePath`/`attractor` reuse `Trails`' exact persistence trick (a persistent per-instance buffer that fades in place and is drawn onto directly, no `seedFrom`/reseed each frame); every point is rendered via the same soft-disc splat technique `Particles` uses (`particleScale.ts`'s shared `particleRadius`, scaled by `dotSize`), so preview and firmware share the identical formula and rendering technique for every variant (the "no algorithm drift" property `Pride2015`/`Pacifica`/`TwinkleFox`/`FormulaField` already rely on) — codegen bakes one dedicated C++ block per selected variant rather than a runtime switch, since the variant is a property, never wired. `formulaType` is scoped to `PROPERTY_META_OVERRIDES.FormulaPoints` rather than the generic `PROPERTY_META` map, since `FormulaField` (field category) uses the same property name for its own, unrelated variant list. See `docs/development/design/formula-pattern-nodes.md`. Not yet hardware-validated.

**Color Trails (stateful advection).** `ColorTrails` (pattern, Audio-Reactive) is adapted from Pygame prototypes by Stefan Petrick, creator of [AnimARTrix](https://github.com/StefanPetrick/animartrix); preserve that credit in UI descriptions, source, README/notices, and generated firmware. `injectionMode` can paint a palette-swept Lissajous segment, a continuously refreshed rainbow perimeter (the "liquid frame"), or both into the prior frame. `flowMode` selects the original scrolling C² 1D Perlin profiles or true 2D Perlin sampling with time on an independent axis, which makes the row/column displacement fields morph organically instead of merely translating. The Y profile shifts each row horizontally into an intermediate CRGB frame, the independently seeded/reversed X profile shifts each column vertically back into the persistent output, then `persistence` applies the very slow fade. Preview and codegen share the same integer gradient hashes, smootherstep, 3× line oversampling, soft endpoint discs, toroidal sampling, and elapsed-time scaling (the source is calibrated at 60 fps). Each horizontal and vertical displacement is capped to ±1 pixel per rendered frame, including audio boosts and delayed-frame scaling, preserving continuous subpixel blends instead of jumping across the trail. The X/Y controls retain the prototype defaults; `displacement` controls warp strength, `endpointSpeed` the line motion, and `colorSpeed` palette travel. Audio inputs are optional: bass strengthens displacement, mids accelerates endpoints, treble accelerates palette travel, and beat drives a short line-endpoint bloom, so autonomous motion remains intact unwired. Firmware declares `buf_cttmp_<id>` as an ordinary render buffer beside the node's persistent output, allowing MatrixOutput PSRAM to offload both; `estimateFirmwareRam` counts both CRGB frames. AnimARTrix itself is CC BY-NC-SA 4.0 rather than MIT; do not import its pattern source directly without preserving that separate license or obtaining Stefan's permission (especially for commercial use).

**AnimARTrix instrument.** `Animartrix` (labelled **AnimARTrix**) is an intentionally isolated CC BY-NC-SA 4.0 integration under `src/animartrix/`, credited to Stefan Petrick and removable without disturbing the MIT core. The initial catalog is Water, Polar Waves, RGB Blobs, Spiralus, and Complex Kaleido. `preview.ts` and `codegen.ts` implement paired normalized-coordinate renderers; keep their equations and smoothing constants aligned. Audio is optional, and unwired nodes remain autonomous. `audioAmount` sets overall reactivity depth: bass changes radial pressure/scale, mids changes angular flow, treble adds spatial detail and colour separation, kick/beat inject radial shocks, snare changes symmetry/arm counts, and hi-hat adds fine shimmer. Generated firmware must retain Stefan's name, upstream URL, and `CC BY-NC-SA 4.0` marker. Do not move derivative mathematics into core files or treat this module as MIT; if Stefan asks for removal, remove the node registration/imports and this directory without changing any microphone or SD-card analysis path.

**Frame Feedback / Delay.** `FrameFeedback` (composite) is the bounded recursive video-synth counterpart to `Trails`: it stores its own output in a fixed ring buffer, reads the output from `delayFrames` ticks ago, optionally fades and transforms that delayed frame (`none`/`translate`/`rotate`/`scale`), then blends it over the live input (`normal`/`screen`/`add`/`multiply`/`difference`/`lighten`). Because the recursion is internal to the node, the graph stays acyclic while still supporting feedback echoes, smeared rotations, and delayed trails. Preview state lives in `frameFeedbackState`; firmware emits a static `_fb_<id>[delayFrames + 1][NUM_LEDS]` ring and copies the produced `buf_<id>` back into it each loop. RAM estimates count that history as internal state: `(delayFrames + 1) × NUM_LEDS × sizeof(CRGB)`. It intentionally remains internal even when MatrixOutput's `usePsram` moves ordinary render buffers to PSRAM, matching the current stateful-node convention.

**Zones (named rectangular regions).** `Zones` (composite) is for installations with multiple logical display areas: it exposes four named zones (A–D, each with an `Enabled` toggle and a normalized 0–1 `X`/`Y`/`W`/`H` rectangle, grouped into collapsible sections via `PROPERTY_GROUPS`) and an optional `base` frame. It seeds its output from `base` (or black), then for each enabled zone with a wired frame, copies that frame's own pixels into the output only within the zone's rectangle — later zones (A→D) paint over earlier ones where rectangles overlap, and a disabled or unwired zone is skipped entirely so partial wiring never punches a black hole in the output. Evaluator and codegen share the same seed-then-paint compositing (the C++ side loops over `WIDTH`/`HEIGHT`-scaled bounds baked from each zone's rectangle at codegen time).

**Fire / Fire2012 shared controls (direction, turbulence, paletteMix, mirror, seed).** Both fire nodes keep their own heat algorithm (`Fire`'s single-neighbor blur vs. `Fire2012`'s classic two-row-lookahead kernel) but share this exact set of five extra controls. Internally, the heat simulation always runs in a canonical primary/secondary grid — primary (`P`) is the distance from the flame base where sparks land, secondary (`S`) is the position across the flame's width — so `direction` (up/down/left/right) only has to remap `(p, s)` back to real `(x, y)` once, at the final palette-sampling step (`firePrimaryLen`/`fireSecondaryLen`/`fireToXY` in `graphEvaluator.ts`); codegen mirrors this with `fireGrid`/`fireXYExpr`, emitting `P`/`S` as the `WIDTH`/`HEIGHT` **macro names** rather than baked JS numbers so the heat array's size stays correct under MatrixOutput's supersample toggle. `turbulence` widens the sideways diffusion window (1 reproduces each node's original fixed kernel width exactly); `paletteMix` blends the palette colour toward plain heat-brightness grayscale; `mirror` folds the rendered frame symmetric across its width (columns for up/down, rows for left/right) as a post-process, same as the zones/mirror pattern elsewhere. `seed` (0 = free-running `Math.random`/`random8()`, unchanged from before this control existed) switches cooling/sparking to a deterministic per-instance LCG (`fireRandom` in the evaluator; a local `_fireLcg_<id>` static in codegen, since FastLED's global `random8()` can't be seeded per-node) so the same seed reproduces the same flame from a fresh start.

**Pride2015 / Pacifica / TwinkleFox (evocative Kriegsman homages).** `Pride2015`, `Pacifica`, and `TwinkleFox` (pattern, Generative) are named after the classic FastLED demos but — like `Plasma` above — are original evocative formulas rather than literal ports of the originals' 16-bit fixed-point/palette-blend/PRNG16 pipelines: `Pride2015` sweeps a full-spectrum rainbow hue across the matrix with a breathing sine brightness wave; `Pacifica` sums a few scrolling sine wave layers through a connected palette (default `ocean`) with a whitecap sparkle where a faster secondary wave crests; `TwinkleFox` gives each pixel an independent twinkle cycle via a deterministic per-index hash (`twinkleHash` in `graphEvaluator.ts`, mirrored verbatim in codegen), coloured from a connected palette (default `party`), with a `density` slider that softens the brightness curve from sparse sharp sparkles to most-pixels-lit. All three use the identical formula on the preview and firmware side (Plasma's approach, not Fire2012's "JS approximates, C++ is exact" split), so there's no algorithm mismatch to track — only the hue-to-color mapping differs cosmetically (`hsv()`/`samplePalette()` vs. `CHSV`/`ColorFromPalette`, same as Plasma). TwinkleFox is not yet hardware-validated.

**Saturation / RGBToHSV.** `Saturation` (composite) scales a frame's per-pixel HSV saturation by `amount` (0–2; 1 = unchanged, 0 = greyscale) — same inline RGB↔HSV extraction as `HueShift` in the evaluator, `rgb2hsv_approximate()`/`CHSV` in codegen. `RGBToHSV` (color) is the inverse of `HSVToRGB`: given a connected color, it outputs `h`/`s`/`v` floats (e.g. to read the hue out of a sampled palette color).

**EncoderInput.** A rotary encoder (e.g. KY-040) alongside `ButtonInput`/`PotInput` — `pinA`/`pinB` quadrature pins plus `pinSW` for the integrated push-button. The preview is a live interactive widget, same as the other two hardware-input nodes: `HardwareInputBody.tsx` renders a pressable button, a draggable pot slider, and a drag-to-turn encoder dial (click doubling as the integrated push-button), writing into `hardwareInputStore` (transient run-state, not a saved property) that `graphEvaluator.ts` reads back via `getState()` each frame — there's no real hardware, but the graph can still be played with live in the browser. Firmware does a polling quadrature decode (a standard 4-bit lookup table, no interrupts, matching this codebase's existing interrupt-free hardware-input style) into an unbounded running `position` count — wire it through `MapRange`/`Mod` to normalise or wrap.

**RTC Clock / Clock Display.** `RTCInput` (input) is the wall clock: `valid`/`synced`/`stale` plus the calendar fields and `secondsOfDay`. Its `timeSource` picks how firmware gets the time — build stamp, a manual seed, NTP, or a battery-backed DS3231 — and **the preview mirrors that choice** rather than always reading the browser clock: `rtcPreviewSnapshot` in `src/state/rtc.ts` runs a Manual seed forward from preview `t` (the stand-in for `millis()`), reports an impossible Manual date as fully invalid exactly like the firmware's `_rtcValidDateTime` guard, shows NTP as UTC plus `timezoneOffsetMinutes`, and simulates a healthy DS3231 with browser-local time because browser preview cannot read the physical bus. `RtcInputBody` renders the node's *published evaluator outputs* (via `previewStore`) so the on-node readout can't disagree with what downstream nodes see. In firmware the first three sources use the free-running software clock — NTP starts from the build stamp (`synced` false, `stale` true) instead of staying dark until Wi-Fi comes up, then the network epoch overwrites the fields once it arrives. DS3231 uses Arduino `Wire` directly at address `0x68` on the board-default SDA/SCL pins, without RTClib; a valid BCD calendar publishes immediately, the chip's oscillator-stop flag controls `synced`/`stale`, and a transient read failure retains the last sample marked stale. `ScheduleTrigger`'s `requireSync` is the way to gate on a *confirmed* sync.

`ScheduleTrigger` (signal) is the other RTC consumer: a time-of-day **Window** (level `active` plus `start`/`end` pulses on the transitions, wrapping correctly past midnight) or a one-shot **Trigger**. Trigger mode fires when its instant is **crossed** — `scheduleState` / the firmware's `_schedulePrevSeconds_`/`_schedulePrevDay_` statics hold the previous usable sample — rather than while inside a one-second window, so a coarse RTC, a slow frame, or a clock correction can't silently skip the day's pulse; a board that boots *after* the instant does not back-fire, and the existing `lastPulseDay` key still caps it at one per calendar day. A `progress` output ramps 0→1 across an active window so a schedule can drive a fade instead of only a hard on/off. `scheduleTimeOfDay` (exported from `graphEvaluator.ts` and used by both sides) clamps each hour/minute/second field to its own range *before* summing — summing first and clamping the total mapped an out-of-range saved value to a different instant in preview than in firmware. `requireSync` is the guard for trusting an unsynced clock, and matters now that NTP firmware runs a build-stamp fallback.

`ClockDisplay` (pattern / Shapes & Text) draws that clock: four digital layouts, two analog ones, and local Stopwatch/Timer transports (which ignore the RTC and keep their own state). It composites over an optional `base` frame like the other Shapes & Text nodes, and publishes `seconds` + `done` so a Timer can drive the rest of the graph. Its text is assembled at runtime, so unlike `Text` (whose string is known at codegen time and baked as columns) the sketch carries a glyph lookup table — **generated from the shared `state/font.ts` data**, never hand-transcribed, along with every string extent (`FONT_W`/`FONT_H`/`TEXT_LINE_GAP`), so preview and firmware layout cannot drift. Codegen treats an unwired `valid` as true whenever `secondsOfDay` is wired, matching the evaluator; with neither wired hardware has no clock at all, so it renders `--:--` and `buildGraphDiagnostics` warns that the preview's browser-clock fallback will not survive a flash. Neither node is hardware-validated yet.

**Field Noise / Frame → Field.** `FieldNoise` (field) is an organic fBm noise source straight as a scalar field — the same octave-summed construction as the `FractalNoise` pattern node (JS: `_snoise2`; firmware: `inoise8`, matching that node's existing preview/firmware noise-algorithm mismatch), just written to the field buffer instead of sampled through a palette, so it sits beside `FieldFormula` as a second raw field generator. `FrameToField` (field) is the inverse of `FieldToFrame`: it extracts a 0–1 brightness field from a rendered frame (average of r,g,b, the same convention `Mask` uses for a mask frame's opacity), so any pattern's output — not just formulas — can drive a downstream `FieldWarp`/`FieldMath`/mask.

**Formula Field.** `FormulaField` (field) is a third raw field generator beside `FieldFormula` (free-text expression) and `FieldNoise` (fBm noise): a `formulaType` dropdown of five curated closed-form fields — `rose` (petal-count trig banding), `superformula` (Gielis filled silhouette — symmetry/n1/n2/n3/a/b), `fibonacciSpiral` (golden-pitch log-spiral arms via `turns`/`tightness`/`bandWidth`), `goldenTiling` (golden-ratio low-discrepancy concentric rings via `density`/`phase`), and `lissajousField` (nearest-sample distance to a Lissajous curve, `LISSAJOUS_FIELD_SAMPLES = 48` points/pixel — comparable per-frame cost to `WaveSim`'s up-to-12 full-grid passes, shared between evaluator and codegen so the sample count can't drift). It has no input ports — every control, including `speed` (0–1, denormalized per-variant via `FORMULA_FIELD_SPEED_MAX` in `speedRange.ts`, the same convention as `Noise`'s `NOISE_SPEED_MAX`), is a baked property, so `cppGenerator.ts` emits one dedicated C++ block for the selected variant at generation time rather than a runtime switch. Every formula is exact closed-form math (`GOLDEN_RATIO`, exported from `graphEvaluator.ts` for codegen to share), so preview and firmware use the identical formula with no approximation gap — the same property `Pride2015`/`Pacifica`/`TwinkleFox` already rely on. See `docs/development/design/formula-pattern-nodes.md`. A separate `PHI` constant was also added to `formulaLang.ts`'s `MATH_CONSTANTS` so any free-text `CustomFormula`/`FieldFormula` expression can reference the golden ratio directly; `cppGenerator.ts` detects `PHI` usage and conditionally emits a matching `#define PHI 1.618033988749895f`, mirroring the existing FastLED-shim (`needsShims`) gating. Not yet hardware-validated. See above for the stateful `FormulaPoints` companion node (phyllotaxis/Lissajous paths, logistic map, attractors) from the same design note.

**MatrixOutput power cap.** MatrixOutput gained an optional `powerLimit` toggle plus `volts`/`milliamps` (the volts/mA editors are gated on the toggle via `isPropertyEnabled`). When on, `cppGenerator.ts` emits `FastLED.setMaxPowerInVoltsAndMilliamps(volts, milliamps)` in `setup()` so FastLED auto-dims to keep PSU draw under the cap. Preview-only (no effect on the live render).

**MatrixOutput hardware settings (FastLED parity).** MatrixOutput also carries `brightness` (0–255, default 200 — the previously hardcoded `FastLED.setBrightness` value; a `PROPERTY_META_OVERRIDES` entry since the shared `brightness` meta is 0–1), `correction` (`none`/`TypicalLEDStrip`/`TypicalPixelString` → `FastLED.setCorrection`), `dither` (default on = FastLED's default, emits nothing; off emits `setDither(DISABLE_DITHER)`), `overclock` (1–1.7× → `#define FASTLED_OVERCLOCK` **before** the FastLED include; clockless chipsets only), and `clockPin` (SPI chipsets only → `CLOCK_PIN` in `addLeds`). The chipset dropdown spans clockless (WS2812B/WS2811/WS2815/SK6812/**SK6812-RGBW**/WS2816/SM16824E/NEOPIXEL) and SPI (APA102/**APA102HD**/WS2801/HD108) parts; `SK6812-RGBW` maps to `SK6812` + `.setRgbw(RgbwDefault())`, and `NEOPIXEL` omits the colour-order template arg (its FastLED alias hardcodes GRB). One shared helper family in `cppGenerator.ts` — `ledHardwareFromProps` (sanitises against the `CHIPSET_OPTIONS`/`COLOR_ORDER_OPTIONS`/`CORRECTION_OPTIONS`/`SPI_CHIPSETS` lists exported from `nodeLibrary.ts`, since these strings land in C++ template args) + `fastledSetupCpp` + `overclockDefineCpp` — feeds all three sketch generators (normal, show controller, music-sync player; the player skips the brightness line because show events drive it). `isPropertyEnabled` gates `clockPin` to SPI chipsets and `overclock` to clockless ones. **Preview:** the master brightness is mirrored on the terminal frame (`applyMasterBrightness` in `LEDPreview.tsx`) so preview matches firmware; correction/dither are deliberately *not* previewed (they compensate the physical LEDs so hardware matches the intent the preview already shows). Not yet hardware-validated.

**MatrixOutput physical layout (`layout`/tiling/custom XY map).** MatrixOutput's `layout` property (`matrix` default / `strip` / `panels` / `custom`) generalises the old serpentine-only wiring remap into `src/state/xyLayout.ts`'s `buildXYTable(width, height, props)`, a pure function returning a grid→physical-LED-index lookup table (or `null` when a plain row-major memmove already does the right thing). `panels` splits the WIDTH×HEIGHT grid into `tilesX`×`tilesY` equal panels; each panel can be rotated 0/90/180/270° via the comma-separated `tileRotations` (row-major panel-grid order) and the panel chain itself can snake via `tileSerpentine` — the existing pixel-level `serpentine` flag still governs the zig-zag *within* each panel (or the whole grid when `tilesX`/`tilesY` are both 1). `custom` takes an explicit JSON permutation of `0..N-1` in `customXYMap`. Invalid layout input is now surfaced explicitly by `validateMatrixLayout()` / `findMatrixLayoutErrors()` (panel divisibility, bad rotation entries/count, bad custom-map JSON/permutations), and `MatrixOutputUpload` blocks upload/export actions until it's fixed; `buildXYTable()` still keeps the old row-major fallback as a last-resort safety net so codegen never emits a broken table. `isPropertyEnabled` in `nodeLibrary.ts` gates the tile/custom-map fields to their relevant `layout` value. Codegen (`cppGenerator.ts`) bakes the table once as a `const uint16_t _xytable[] PROGMEM` plus an `XY(x,y)` reader — a single code path that replaced the old serpentine-only formula, so pixel serpentine, panel tiling, and a custom map compose freely. Since physical wiring order never changes *what* renders at a given (x,y) — only which LED index it's written to — the live preview needs no changes to stay correct for the pixel content itself. `LEDPreview.tsx` does draw a purely cosmetic panel-boundary overlay for valid `layout === 'panels'` setups: `matrixTileLayout()` (`graphStore.ts`, memoised like `matrixDims`) returns the `tilesX`×`tilesY` grid only when the panel layout validates, and a second `<canvas>` stacked on top of the main one (`.canvasStack`/`.tileGridOverlay` in `LEDPreview.module.css`) is redrawn only when the tile grid or canvas size changes — not every animation frame — so it costs nothing during normal playback; tile rotation/chain order isn't reflected since neither affects the rendered content. **Hardware-validated** for `layout: strip` on an ESP8266 (NodeMCU, 10×1 WS2812B strip) via `arduino-cli` (2026-07-25, `hw-f57928b9`): compiled, flashed, and confirmed correct color order, orientation, brightness, and power cap. `panels` and `custom` remain not yet hardware-validated.

**MatrixOutput PSRAM buffers (`usePsram`/`psramMode`).** For designs whose static buffers overflow the ESP32's internal DRAM (`dram0_0_seg` link errors), MatrixOutput carries a **Use PSRAM** toggle rendered in `MatrixOutputUpload` — *not* the generic property list, because visibility depends on the selected board: `Board.psram` in `uploadStore.ts` lists each board's PSRAM FQBN options (S3: OPI `PSRAM=opi` / QSPI `PSRAM=enabled`, picked via `psramMode` since the interface is a module-package fact that can't be probed from the host; plain ESP32: QSPI only). When on, both generators declare the per-node `buf_`/`field_` render buffers (and the show sketch's `showA`/`showB` + per-pattern buffers) as pointers allocated via the shared `_psAlloc` helper (`PSRAM_ALLOC_CPP`/`psramBufferDecl` in `cppGenerator.ts`) — `ps_malloc` with internal-heap fallback via a runtime `psramFound()` check — and `runUpload` appends the chosen PSRAM option to the FQBN. `leds` always stays a static internal array (FastLED's ESP32 drivers read it from ISR/DMA context where PSRAM access can fault). The `psramAllowed: false` codegen opt (passed when the selected board has no PSRAM) neutralises a stale toggle so AVR/RP2040 sketches never see ESP32-only calls. Stateful nodes' `static` in-loop arrays (ReactionDiffusion, GameOfLife, …) still live in `.bss` — a follow-up. Not yet hardware-validated. Related: the upload helper's failure banner is phase-aware (`_compile_upload` returns `(rc, phase)`) — a build failure says nothing reached the board; only an upload failure suggests download mode.

**Firmware RAM estimate.** `estimateFirmwareRam()` (`src/utils/validateGraph.ts`) gives a pre-upload RAM budget: it walks backward from MatrixOutput through `edges` to find every node that actually feeds the sketch (an unreached node gets no buffer in codegen, so it's excluded), sums the physical `leds` array plus each reachable `frame`/`field` render buffer (including ColorTrails' second CRGB advection buffer, and excluding a terminal node that aliases `leds` — see the codegen section above; the alias conditions are restated there rather than shared, because codegen checks expression-resolved properties it derives internally, and a disagreement over-counts by one frame, which is the safe direction for a budget), and adds known per-LED overhead for the handful of simulation nodes whose `static` state is bigger than their own render buffer (Fire2012's heat map, Game of Life's cell/next/bright grids, Reaction-Diffusion's four u/v grids, WaveSim's p/c/n grids) plus Particles' fixed-size pool (independent of matrix size). Since that stateful state always stays in internal `.bss` regardless of PSRAM (see above), the estimate is split into `internalBytes`/`psramBytes` by MatrixOutput's `usePsram` toggle. `MatrixOutputUpload` shows a compact KB readout next to the power estimate, and `validateGraph` warns when the internal estimate crosses a conservative heads-up threshold, nudging toward enabling PSRAM. It's a rough guide, not a linker-accurate figure — the post-compile flash/RAM report from the build engine remains the ground truth, which the live controller-capacity meter below surfaces directly rather than estimating.

**Live controller-capacity meter.** `POST /api/compile-check` (`backend/app.py`) runs a real compile-only build — same engine, same sketch generator, no port so nothing is flashed — via the existing `_compile_upload`/`_compile_upload_fbuild` generators (already support `port=""` as "compiled only"), drained synchronously by `_drain_compile` into one JSON result instead of a streamed log: `_size_bytes_report` (arduino-cli: `Sketch uses…`/`Global variables use…`) and `_fbuild_size_bytes_report` (fbuild: `Flash:`/`RAM:`, unit-converting KB/MB/bytes) return `{usedBytes, limitBytes, percent}` per flash/RAM, and `overflow` reuses the existing linker-overflow marker check. Two fbuild-specific correctness fixes, both found by live-testing against the real toolchain: (1) fbuild's project scaffold is one shared directory, so two overlapping compiles (a live re-check racing another check or a real Upload) used to interleave `main.cpp` writes and build output and corrupt each other's result — `_fbuild_build_lock` now holds for the whole duration of every `_compile_upload_fbuild` run, serializing all fbuild compiles project-wide. (2) fbuild only reprints its `Flash:`/`RAM:` line when it actually reruns the linker, so a no-op incremental build (nothing changed since the last check — the common case once the debounce settles) silently produced no size report at all; `_fbuild_cached_size()` falls back to fbuild's own persisted `.fbuild/build/<env>/release/.firmware_size_cache.json` when the live build output has none. `src/state/capacityStore.ts` debounces requests 1200 ms and caches by board target (fqbn + any PSRAM option) plus a hash of the generated sketch — switching boards invalidates immediately so a reading is never shown against the wrong target — exposing `checking`/`measured`/`stale`/`toolchain-missing`; a completed 'measured' result's own `ok`/`overflow` flags (read via `src/utils/capacityFormat.ts`'s `summarizeCapacity`) distinguish a healthy percentage from "won't fit" from an unrelated compile error, so there's no separate status enum value per outcome — that same tooltip surfaces the compile-check's log tail on failure for debugging. On overflow, `summarizeCapacity` shows the actual over-100% usage in red (`SRAM 112%`) rather than a bare "won't fit" when a figure is available. A genuine overflow is normally a **hard linker failure** — `ld` refuses to produce an `.elf` at all, so fbuild never reaches the step that prints its own `Flash:`/`RAM:` summary (confirmed with a real forced ESP32-S3 DRAM overflow: no size line anywhere in the log, only `ld`'s `region 'dram0_0_seg' overflowed by N bytes`). `_fbuild_overflow_estimate()` derives a real percentage from that same linker message plus fbuild's own board-memory line (`Memory: 8.00MB Flash, 320.00KB RAM`, printed up front regardless of outcome) — region names containing "ram" attribute to RAM, everything else to flash — wired in as `/api/compile-check`'s last fallback when a failed compile produced no size line at all. Falls back to the plain "won't fit" text only when even the linker gave no parseable overflow amount. `summarizeCapacity` always reports **both** metrics together (`flash P%`/`flash n/a` and `SRAM P%`/`SRAM n/a`) in every outcome rather than showing whichever one happened to be available — a design flipping from "SRAM 101%" (failing to link) to just "flash 10%" (succeeding) used to silently swap which metric the meter displayed (successful ESP32/fbuild builds routinely self-report an "impossible" RAM figure that `_fbuild_cached_size` discards as unreliable, while a failed build's overflow percentage has no such guard), reading as "the RAM problem is fixed" when RAM had simply stopped being measurable; pairing both figures unconditionally means that gap can never be mistaken for good news. `MatrixOutputUpload.tsx` (the always-mounted node body, not just the upload popup) generates the sketch and drives the check continuously while composing, rendering the compact meter (`Arduino Uno · flash 74% · SRAM 41%`); `MatrixOutputDeployPopup.tsx` reads the same store passively (repeat requests with an unchanged board+code are no-ops in the store, so both components triggering costs nothing extra) and folds a confirmed overflow into its `blockingErrors`, making the measured result — not the fast heuristic above — the authority for whether Upload is allowed. `PatternCollectionBody.tsx` shows the flash/RAM delta between the last two same-board measurements (`capacityDelta`/`formatCapacityDelta`), so adding or removing a pattern surfaces what it cost once the next check lands. Not yet hardware-validated.
