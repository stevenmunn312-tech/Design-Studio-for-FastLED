# App review — 24 September 2026

Implementation checklist for the desktop product and usability review of the
`Hardware` branch. Work through the numbered items in order. This is the detailed
plan for the app review; [todo.md](todo.md) remains the wider hardware/release
backlog. The separate code-review defects are outside this checklist.

The aim is to make the existing creative-to-hardware workflow easier to discover,
understand and trust. Preserve the illuminated visual identity, physical component
imagery, typed graph connections, reusable patterns and generated Build Diagram.

All items start unchecked. Check an item only after its stated outcome has been
verified; adding the UI alone is not completion.

## 2. Make readiness and connection states precise

6. [x] **Replace premature capacity verdicts.** Show “Capacity unknown” or
   “Capacity not checked” until a valid measurement exists. Distinguish checking,
   measured fit, measured overflow and failed measurement. Never display “FITS”
   alongside “capacity not checked”. Review `src/components/StatusBar/`,
   `src/components/Preview/HardwareReadiness.tsx` and the Upload workspace.
   `summarizeCapacity` now returns a verdict. Both the status-bar chip and the
   Upload line lead with it: Capacity (no measurement), Checking, Fits, Tight,
   Too big, Check failed, or Last check for a reading of an older graph. Only
   a current fit is coloured as a pass. All seven states were checked in the
   browser by setting the store directly, with no compile. The review also
   found that the Upload line had been squeezed to a 2 px rule and never
   displayed; that is fixed. Unit tests cover every state and both layout
   causes.

7. [x] **Separate port selection from connection.** Present a remembered but absent
   port as “COM6 selected · disconnected”, or equivalent wording. Use the same
   distinction in the upload heading, readiness details and footer. Verify absent,
   connected, disconnected-after-selection and refreshed-port states.
   `describePort` in `src/utils/portStatus.ts` now supplies the port wording
   for the Upload heading, the Connection readiness row, the footer chip, the
   Board popup, the setup wizard and the serial toolbar. It has five states:
   checking, helper offline, no port selected, "COM6 selected · disconnected"
   and "COM6 · connected". A new `portsScanned` flag keeps an empty list read
   as "checking" until the first scan returns. Against the real helper that
   first scan took about 10 s, and before this change the footer said "Not
   detected" for all of it. The serial monitor's own state now reads
   Monitoring / Monitor off, so it cannot contradict the port wording. All
   states were checked in the browser against the live helper with no board
   attached, and by setting the store for connected and offline. Unit, store
   and component tests cover every state and a refresh restoring a replugged
   port.

8. [x] **Separate the different kinds of readiness.** Make preview activity, graph
   validity, compile capacity, connection and hardware verification independently
   understandable. A working preview must not imply successful compilation or
   physical verification. Derive support claims from the existing
   [support matrix](docs/release/beta-support-matrix.md).
   A new **What is established** list in the Upload controls comes from
   `readinessLayers` (`src/utils/readinessLayers.ts`). It shows Preview,
   Graph, Capacity, Connection and Hardware as separate rows, each with its
   own reading and a glyph as well as a colour. Each row opens with the
   keyboard or pointer to say what it proves and what it does not. The graph
   error count is the deploy gate's own list, and the warning count matches
   Graph Health. Hardware reads "Recorded on hardware" only when the setup
   has no coverage gaps against the recorded rows that mirror the support
   matrix; otherwise it names the gaps and says that a compile or upload does
   not verify them. The tools expander no longer says "Ready to upload"; it
   is now **Build tools & port**, with a Ready badge. The preview HUD chip
   now reads Browser preview instead of Signal live. Checked in the browser
   against the live helper. Unit and component tests cover each row, and a
   live preview with nothing else established shows no other row as
   established.
   *Revised 2026-09-26 after Steve's review of a real project, which read as a
   wall of red and orange.* The Hardware row is gone. Almost every setup is
   untested by this project, so the row was orange for nearly everyone and
   gave them nothing to act on. Tested builds are listed in the README and the
   support matrix, with an invitation to open a GitHub issue. The list is now
   **Getting to your board**, with four rows that say what comes next. A clean
   graph reads Ready, and warnings read as suggestions. The report form no
   longer opens by itself after an upload; **Share a report…** invites one.
   The tone rules behind this, which govern items 9 onward, are: red only for
   what blocks the action you are taking, a fix button wherever the fix is
   knowable, say each thing once, and "not yet" is not a fault.

9. [x] **When an action is blocked, say why once and offer the way through.**
   Beside a disabled Upload or Flash, give one short reason and the button that

   capacity reading says it is waiting rather than "Check failed".
   Done 2026-09-26: a blocked Upload/Flash button is now quiet grey rather
   than green. One sentence under it names the first thing in the way, with
   the button that clears it, and it is linked as the button's description.
   `uploadBlockReason` (`src/utils/uploadBlockReason.ts`) decides the order:
   something to upload (**Go to Graph**), trust (**Trust it**), graph fixes
   (**Show me**), display images, size, then the Build tools & port rows,
   each with its own action (**Retry helper**, **Fix engine**, **Install

## 3. Turn diagnostics into guided repairs

10. [x] **"Here is the problem — want me to fix it?"** Every diagnostic states
    the problem in plain words, then the next step, and offers a button that
    performs the repair wherever Studio can know it (undoable). Replace advice
    that points back at its own message, and remove refusals of things the
    firmware could simply honour. Keep Graph Health and Upload wording
    consistent through the shared diagnostic model.
    Progress 2026-09-26:
    - Trust now follows where content came from: anything shipped or made on
      this machine is trusted, and a Trust button is remembered for good.
    - The SD player honours an LED output's fixed brightness and on/off
      instead of refusing them.
    - A power cap working as designed is no longer flagged.
    - Template controls wire themselves, and unconnected ones get one
      **Connect them** card per screen.
    - The two "Follow the … named in the message" fixes are now the message's
      own next step.
    - Graph Health says "to fix" and "suggestions" instead of "errors" and
      "warnings", suggestions use a calm colour, and Fix reads Next step.
    Sweep done 2026-09-26. These cards now have a button where the fix is
    knowable (each is undoable, and each re-checks before acting):
    - A pin the board doesn't support or bring out: **Move to a free pin**
      (`movePartPinToFree`), through the same safe-pin assignment a new part
      uses, keeping the capability the role needs.
    - A show with nowhere to go and exactly one free LED output: **Connect
      it**.
    - A Music Player with no patterns: **Add a collection**, which reuses an
      idle collection already on the canvas or adds and wires a new one.
    - A large fixture with no power cap: **Open Board settings**. The supply
      rating is the user's to enter, so Studio does not guess it.
    Deliberately left as advice, because the fix depends on what the author
    meant: which of two jobs a control keeps, whether to delete a disconnected
    node, how to route a wired control a build can't read, and a panel that
    can't be switched back on (see CLAUDE.md). Checked in the browser: a button
    on GPIO 27 on an ESP32-S3 moved to GPIO 5 with one click, the card
    cleared, and undo put it back. `graphHealthRepairs.test.ts` covers each
    repair and that its card goes away.

11. [x] **Navigate to the actual cause.** Where a diagnostic concerns a connection,
    focus and highlight that connection and its relevant nodes. Where it concerns
    screen controls, offer a direct route such as “Open screen controls”. Preserve
    “Locate node” for findings where the node itself is the useful destination.
    Start with the observed custom-screen/fixed-Touch-Controls failure.
    Done 2026-09-26. A diagnostic can now name the wires at fault (`edgeIds`)
    and the screen it is about (`screenDesignId`). **Show the wire** frames
    the wire's two ends and lights the wire while dimming the rest, and the
    next click on the canvas clears the highlight (`locatedEdgeIds` in
    `uiStore`). **Open screen design** opens that panel's design in the
    designer. Several cards use them:
    - A Map Range signal-range card names its wire.
    - The two firmware checks ("Output firmware cannot honour these
      controls" and "Display firmware…") now find the node their message
      names. Output cards show only the wires into that output's runtime
      inputs; display cards show the panel's and its Touch node's wires and
      can open its screen. Previously these framed every LED output or every
      display on the canvas.
    - The template-controls and inert-control cards open their screen.
    **Locate node** stays wherever the node itself is the answer. Checked in
    the browser: on a Music Player build, a button wired into an LED String's
    Enabled showed that one wire lit, with everything else dimmed.
    `graphHealthLocate.test.tsx` covers the wire, the highlight and the
    screen route.

12. [x] **Verify a complete repair journey.** Starting in Upload with that blocking
    touch error, follow the diagnostic to the relevant graph or designer context,
    correct the wiring and return to Upload. Confirm that validation updates and
    the blocker disappears without a reload. Add a focused navigation/repair test;
    keep graph-changing repairs undoable.
    Done 2026-09-26. The journey uses a Music Player build whose touch screen's
    **Controls** are wired into the LED output. The player owns the lamp, so its
    firmware cannot read that wire and Upload is blocked. That wire now has an
    unambiguous repair, **Move the wire** (`routeControlsToEngine`). It moves
    the Controls wire onto the engine's own Controls input, which carries the
    same lamp commands. It is offered only when that is the single offending
    wire and the engine's input is free. A wire into Enabled or Brightness
    stays advice, because it needs a mapping.
    Walked in the browser with no reload:
    1. The Upload tab said "9 things to fix first" with **Show me**.
    2. Graph Health's card led with "Move the Controls wire onto Music
       Player…". **Show the wire** lit the Touch → LED String Controls wire.
    3. **Move the wire** moved it, and the matching "Display firmware…" card
       from the panel's side cleared with it.
    4. Upload then read 7 (only pin cards from that bench's S3 board were
       left). Undo put the wire back and returned the count to 9; redo
       restored 7.
    `repairJourney.test.tsx` holds the same journey against the real
    validator, deploy gate, drawer and store. It checks that Upload ends fully
    unblocked, and that undo and redo hold. While building it, cards whose
    message names a widget ("Panel.Play: …") were not matched to their node;
    they are now.

14. [x] **Explain starter requirements before loading.** Add concise difficulty

    Done 2026-09-26. Every starter carries a `guide` (`StarterGuide` in

15. [x] **Provide a short, optional first-project sequence.** Guide users through
    choosing a starter, changing its appearance, selecting the board and LEDs,

    tools and readiness checks. Each step should open the relevant workspace and

    Done 2026-09-26. A **First project** card (`FirstProjectGuide.tsx`) with
    five steps: Choose a starter, Make it yours, Choose your board and LEDs,
    Check it's ready, Upload. It is offered from three places: the Start
    Gallery ("Guide me from here to my board"), the empty Graph start screen
    ("Guide me, step by step") and File ▸ First Project Guide.
    - Each step is read off the project, not ticked by the guide
      (`src/utils/firstProjectSteps.ts`), so work done with the guide closed
      still counts.
      - A project that already has content counts as its own starter and is
        never replaced.
      - "Make it yours" compares node settings and wires against the
        project's shape when it started, ignoring positions.
      - The board step is done once the Board names a profile.
      - Ready means no deploy blockers and a capacity check that fits.
      - Upload is done when a project upload finishes. A wiring test or
        calibration sketch does not count (`uploadStore.statusIsProject`).
    - Each step's buttons open the existing tool: the Start Gallery, Graph,
      Hardware, LED setup (the setup wizard) or Upload. The guide never loads
      anything itself, and a button for the tab you are already on is left
      out.
    - Any step can be skipped ("Skip for now") and picked up again ("Back to
      it"). The compact strip shows the current instruction; **All steps**
      opens the complete list above it. It closes and resumes where it was,
      including after a reload.
    - With no board connected, the last step ends on a plain instruction, for
      example "COM6 isn't there right now. Plug the board in with a USB
      cable, or choose its port on the Upload tab."
    - The strip spans only the visible workspace between the two floating side
      panels. The graph's fit frame, minimap and zoom controls use its measured
