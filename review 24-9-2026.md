# App review — 24 September 2026

Implementation checklist for the desktop product and usability review of the
`Hardware` branch. Work through the numbered items in order. This is the detailed
plan for the app review; [todo.md](todo.md) remains the wider hardware/release
backlog. The separate code-review defects are outside this checklist.

The aim is to make the existing creative-to-hardware workflow easier to discover,
understand and trust. Preserve the illuminated visual identity, physical component
imagery, typed graph connections, reusable patterns and generated Build Diagram.

All items start unchecked. Check an item only after its stated outcome has been
verified; adding the UI alone is not completion.

## 1. Establish the baseline and give the active task more room

1. [ ] **Capture repeatable review scenarios.** Use disposable projects for a blank
   workspace, Juggle driving an LED String, a music player with a display, a graph
   with one blocking error, and an empty screen design. Record screenshots at
   1920×1080 and 1366×768 so later layout changes can be compared consistently.

2. [ ] **Make Graph Health compact by default.** Show the issue count and highest
   priority issue in a compact summary; expand details on demand. Size the expanded
   drawer to its content with a sensible maximum and internal scrolling. One short
   error must not reserve roughly a third of the workspace height.
   Start in `src/components/GraphHealth/`.

3. [ ] **Use workspace-specific panel defaults.** Keep the live preview prominent
   in Graph. Give Hardware, Upload and Build Diagram more room by starting their
   secondary preview/audio panels collapsed or compact. Preserve explicit user
   resize and visibility choices per workspace; returning to a tab must restore
   those choices. Review `src/App.tsx`, `src/state/uiStore.ts` and
   `src/components/Layout/` together.

4. [ ] **Reduce persistent decoration and idle controls.** Reduce the large logo
   area in the preview panel and compact idle spectrum/transport content where it
   does not help the current task. Keep audio controls readily available when the
   user is auditioning or performing. Verify that reclaimed space actually enlarges
   the useful canvas, diagram or console.

5. [ ] **Verify usable working space.** Repeat the baseline scenarios at both
   viewport sizes. Check graph zoom/fit, hardware inspectors, diagram labels,
   sidebar scrolling and console visibility. Confirm that panel changes do not
   clip controls, hide focus or break workspace switching.

## 2. Make readiness and connection states precise

6. [ ] **Replace premature capacity verdicts.** Show “Capacity unknown” or
   “Capacity not checked” until a valid measurement exists. Distinguish checking,
   measured fit, measured overflow and failed measurement. Never display “FITS”
   alongside “capacity not checked”. Review `src/components/StatusBar/`,
   `src/components/Preview/HardwareReadiness.tsx` and the Upload workspace.

7. [ ] **Separate port selection from connection.** Present a remembered but absent
   port as “COM6 selected · disconnected”, or equivalent wording. Use the same
   distinction in the upload heading, readiness details and footer. Verify absent,
   connected, disconnected-after-selection and refreshed-port states.

8. [ ] **Separate the different kinds of readiness.** Make preview activity, graph
   validity, compile capacity, connection and hardware verification independently
   understandable. A working preview must not imply successful compilation or
   physical verification. Derive support claims from the existing
   [support matrix](docs/release/beta-support-matrix.md).

9. [ ] **Make blocked actions visibly blocked and explain why.** Strengthen the
   disabled treatment of Upload/Flash actions and place a short reason next to
   the action. Keep detailed diagnostics accessible by keyboard and pointer,
   rather than relying only on a disabled button's tooltip. Add focused tests for
   readiness state transitions and consistent labels.

## 3. Turn diagnostics into guided repairs

10. [ ] **Lead each blocking diagnostic with the next action.** Structure the
    message as the problem, the immediate repair and optional technical detail.
    Replace generic advice such as “Follow the wiring or export-path change” with
    the specific repair already known to the validator. Keep Graph Health and
    Upload wording consistent through the existing shared diagnostic model.

11. [ ] **Navigate to the actual cause.** Where a diagnostic concerns a connection,
    focus and highlight that connection and its relevant nodes. Where it concerns
    screen controls, offer a direct route such as “Open screen controls”. Preserve
    “Locate node” for findings where the node itself is the useful destination.
    Start with the observed custom-screen/fixed-Touch-Controls failure.

12. [ ] **Verify a complete repair journey.** Starting in Upload with that blocking
    touch error, follow the diagnostic to the relevant graph or designer context,
    correct the wiring and return to Upload. Confirm that validation updates and
    the blocker disappears without a reload. Add a focused navigation/repair test;
    keep graph-changing repairs undoable.

## 4. Make the first successful project easier to reach

13. [ ] **Promote a recommended first starter.** Make Juggle the clearest beginner
    entry in the Start Gallery while keeping Blank Canvas readily available.
    Preserve the existing concrete “change a control, insert Trails, add Mirror”
    teaching sequence.

14. [ ] **Explain starter requirements before loading.** Add concise difficulty
    and required-hardware information, distinguishing what can be previewed in
    the browser from what needs hardware to deploy. Give music-player and SD-show
    starters especially clear prerequisites.

15. [ ] **Provide a short, optional first-project sequence.** Guide users through
    choosing a starter, changing its appearance, selecting the board and LEDs,
    checking readiness and uploading. Reuse the Start Gallery, existing setup
    tools and readiness checks. Each step should open the relevant workspace and
    let the user skip or resume without replacing existing work.

16. [ ] **Walk the beginner route from a clean session.** Verify that a first-time
    user can reach a working preview and understand the next deployment step
    without reading repository documentation. With no board connected, end with
    a clear connection instruction rather than an unexplained disabled action.
    Cover starter loading and project preservation with focused tests.

## 5. Clarify navigation, terminology and visual hierarchy

17. [ ] **Distinguish performance tools by purpose.** Give Performance mode,
    Performance Deck, Stage and the performance monitor clearly distinguishable
    labels. Group related tools and preserve their keyboard shortcuts. A user
    should be able to predict what each control opens without trial and error.

18. [ ] **Rebalance the main toolbar.** Give the active workspace's primary action
    greater emphasis and reduce the prominence of occasional actions such as
    Share. Make the relationship between the Upload shortcut and Upload tab
    obvious. Keep secondary actions discoverable as the window narrows.

19. [ ] **Improve everyday reading and keyboard use.** Increase small operational
    text and weak contrast where needed, especially diagnostics, node controls
    and status labels. Keep colour as a supporting cue rather than the only cue.
    Verify visible focus, accessible names, keyboard navigation and zoomed text;
    preserve the app's existing visual character.

## 6. Improve the screen designer's starting experience

20. [ ] **Put templates on the empty screen.** Offer “Start with a template” in the
    empty designer canvas alongside the option to add individual widgets. Surface
    templates appropriate to the panel's connected source before unrelated ones,
    using the existing template/source mapping.

21. [ ] **Explain appearance and behaviour separately.** Make it clear which
    controls change a widget's appearance and which connect it to a graph value
    or action. Show whether a control is connected and provide a direct route to
    its graph wiring. Use user-facing language in place of unexplained terms such
    as “graph-facing roles”. Start in `src/components/DisplayEditor/`.

22. [ ] **Verify the template-to-live-control journey.** Insert an appropriate
    template in a disposable project, connect its controls through the existing
    workflow, open Run and confirm that an interaction reaches the intended graph
    destination. Check return navigation, undo and save/reload. Keep browser
    interaction evidence separate from any physical-device verification.

## 7. Align documentation and complete the product pass

23. [ ] **Update instructions to match the workspace tabs.** Correct descriptions
    of a lower hardware bench beneath the graph in [README.md](README.md) and
    [the hardware guide](docs/user/hardware-workbench.md). Update affected in-app
    help, starter instructions and screenshots to use the final labels and
    Hardware / Graph / Upload / Build Diagram navigation. Search for obsolete
    wording rather than assuming those two documents are the only occurrences.

24. [ ] **Run the final acceptance walkthrough.** Repeat all baseline scenarios
    after the changes, including narrow-window and keyboard checks. Confirm that
    the active task has usable space, every blocked action has a clear next step,
    and unmeasured or unverified states are labelled honestly. Run the relevant
    automated checks and production build. Record outcomes and remaining issues;
    do not mark physical upload or hardware behaviour verified without a device
    test. Any firmware compile checks follow the repository's on-request,
    one-at-a-time workflow.
