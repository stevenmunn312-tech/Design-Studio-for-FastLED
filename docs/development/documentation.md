# Maintaining documentation

Use [the documentation index](../index.md) as the entry point. Link to the
nearest authoritative document instead of copying a subsystem explanation.

## Choose a home

| Material | Location |
| --- | --- |
| Installation and first successful task | `docs/getting-started/` |
| Task-oriented product instructions | `docs/user/` |
| System boundaries and cross-cutting contracts | `docs/architecture/` |
| Numbered architectural decisions | `docs/architecture/decisions/` |
| Feature semantics and rationale | `docs/design/` |
| Lookup tables, API behavior and generated references | `docs/reference/` |
| Implementation rules and repeatable testing | `docs/development/` |
| Unfinished rollout detail and candidate roadmaps | `docs/plans/` |
| Repeatable diagnosis and maintenance | `docs/runbooks/` |
| Compile results, physical bench records and reviews | `docs/reports/` |
| Support promises, release procedure and release gates | `docs/release/` |
| Superseded context with no live ownership | `docs/archive/` |

Root [todo.md](../../todo.md) owns active project ordering. A detailed plan may
own its steps, but do not repeat the same checkbox status in several documents.
Feature design owns behavior and rationale; reports own dated results.
The [support matrix](../release/beta-support-matrix.md) alone promotes a hardware
combination from experimental to supported. Compilation is not physical validation.

Keep [CLAUDE.md](../../CLAUDE.md) concise and route subsystem detail to
`development/patterns/`. Its existing tests enforce that every patterns file
is linked and that the always-loaded guidance stays small.

## Names and lifecycle

Use lowercase ASCII, hyphen-separated filenames and directories. Use stable
topic names for maintained guides, `YYYY-MM-DD-topic.md` for dated reviews,
and immutable zero-padded IDs for ADRs. Avoid spaces, underscores and vague
suffixes such as `final`, `new` or `handoff`.

Preserve conventional entry points (`README.md`, `CONTRIBUTING.md`,
`SECURITY.md`, `CHANGELOG.md`, `AGENTS.md`, `CLAUDE.md`), tool `SKILL.md`
files and legal filenames. Keep licenses with their assets and leave third-party
documentation, packaged copies and ignored private documents outside this hierarchy.

State the applicable branch or release where behavior differs. Plans should
identify open work and its owner; evidence should identify the source revision,
date, toolchain and exact hardware where known. Distinguish implementation
status, compile results and physical validation. Do not invent verification dates.

A completed implementation does not make its design document obsolete.
Archive only when a document no longer owns a live contract or unresolved task;
preserve evidence used by a support claim. Keep decisions and unique constraints
before consolidating repeated background.

## Moving and generating documents

Update relative links from the moved page as well as links to it, including
images, source files and section anchors. Update the index, code comments,
scripts and published links that consume a renamed path. Preserve links to a
frozen release branch or historical commit when that is their intended context.

Use an intermediate filename for case-only renames on Windows. For a known
published URL that must stay usable, retain a short pointer or a hosting redirect,
not a second full copy of the document.

[Node cards](../reference/node-cards.md) are generated by
`scripts/generate-node-card-svgs.ts`; regenerate through `npm run gen:node-cards`
when its inputs change. Its output path and `public/node-cards/` assets are
intentional. The [property-input audit](../reports/reviews/property-input-audit.md)
is a historical snapshot, not a live generated inventory.

The desktop builder reads `desktop/bundle-readme.txt` and distributes it as
`README.txt`. Edit the source and rebuild future bundles rather than modifying
copies under `release/`.

Before submitting, check local links and anchors, stale paths, image references
and affected tooling, then run the repository's required validation commands.
